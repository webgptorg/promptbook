# Promptbook (`ptbk`)

Promptbook is one npm package, `ptbk`, providing the `ptbk` command-line utility. It operates a Git-backed project of three Book entities: **agents**, **tasks** and **chats**. Canonical Books start with `AGENT <name>`, `TASK <name>` or `CHAT <name>` and share commitment syntax. Normalized opening-name content is logical identity, not a generated ID or filename key. System-created task/chat names include readable creation date/time without mandatory timestamp grammar. `chats/` holds conversations, Git-versioned `ptbk.json` holds configuration, ignored `.ptbk/` holds runtime state and `traces/<task-file-basename>/` holds evidence under the literal source filename without final `.book` or legacy `.md`.

## Core operating principles

**[User control takes priority](concepts/user-control.md)** whenever the user intervenes. Preserve their active work and give their current instructions precedence over conflicting agent actions. An explicit takeover protects the affected resource while independent authorized work continues. For a browser tab, the user decides when to hand control back.

**[External-action impact](concepts/external-action-impact.md)** uses a decimal logarithmic scale, executing-agent evaluation and deterministic aggregation/30-day aging. The External activity log records logical operations including failed attempts, groups inherent batches by default and offers ungrouped/task/agent views. **[Shared common knowledge](concepts/common-knowledge.md)** lives at `https://ptbk.io/book` with its own release cycle; project Adam references it and internal Expert inherits that project Adam, so Teacher receives it transitively. User forks/pins and historical evaluation provenance remain intact.

**[Autonomy and minimal interruption](concepts/minimal-interruption/_index.md)** is foundational across the system. Its dedicated knowledge directory contains the operator/staff analogy, decision rules, authentication/technical/content examples and acceptance cases. Active attention requires a concrete human decision/input/action; inspectable progress, significant completion and autonomous repair alone do not qualify. Every attention-producing condition has a [responsible agent](cli/notifications.md#ownership-and-continuing-relevance): its creator, or Fixer for system/orphaned notices. The owner supervises continuing relevance through shared [progressive waiting](concepts/progressive-waiting.md), withdraws obsolete waits and appends the reason to the originating chat without rewriting history or cancelling user input; automatic agent checks respect Pause. The existing dashboard preserves voluntary inspection and final operator control. Tasker, Router and working agents receive the applicable knowledge through ordinary context. [Content/system purpose](concepts/minimal-interruption/work-purpose.md) is relative to project scope and independent of core provenance or engine-owned definitions; [TASK PURPOSE](book-language/commitments/task-purpose.md) changes append to the Book with source-preserved history.

**Automatic repair and useful unattended operation are foundational.** The engine's [autonomy and minimal-interruption principle](concepts/engine-and-project.md#autonomous-operation-and-minimal-interruption) targets sustained useful unattended work, including a year-long agenda: attention is exceptional, a response clears its question promptly, and one waiting operation does not stop independent work. A started project should progress authorized work and solve routine problems with as little unnecessary user involvement as possible. Completed setup with required access should suffice without later routine dashboard configuration. Agents adapt authorized service/interface workflows and recurring sends/submissions without repeated approval. Cause-aware bounded retry bursts lead to autonomous repair or scheduled rechecks, never a generic human Retry question merely because a counter expired; unresolved/judgment-dependent problems go to the ordinary editable OPEN **Fixer**. Its simple initial Book aims to solve general problems and offload decisions, with User and Expert in its team. Consultation and learning are normal agent mechanisms. Users may customize all/some/no-User consultation; no special Fixer channel, privileged worker or hardcoded escalation policy is introduced. See [automatic repair](concepts/automatic-repair.md), [Fixer](agents/core-agents/fixer.md) and [unattended operation](cli/autonomous-operation.md).

Every engine owns one concrete project directory; exclusive locking prevents two local owners across installations. It runs with zero or many observing clients and contains coherent internal **sub-engines** rather than another global worker. Health is exactly one sub-engine per project engine; browser/harness domains may manage multiple named resources. Shared lifecycle states remain **running, pausing, pause and stopping**. Pause blocks new task claims/continuations and requests supported interruption of active task sessions; ordinary Stop finishes/checkpoints owned work toward shutdown. Pending intent can be cancelled/changed. Force stop is immediate with best-effort owner cleanup; external hard kill has no cleanup guarantee. Enabled persistence restores all still-registered services at OS reboot: prior running/Health-only agendas may work after current checks, while manual/combined pause, stop, force stop and panic outcomes start directly paused before any task claim. Unexpected disappearance/ambiguous external kill never authorizes automatic work resumption; any recovered service is paused. Stop/panic still ends the current process and prevents immediate replacement. `ptbk start --paused` exposes the same availability-without-queued-work policy; no-persist/foreground opt-outs remain honored. A dashboard is a lightweight cockpit/view/controller, never an independent scheduler: opening/closing one does not start/stop the engine. A running engine can legitimately wait for tasks or tools without being technically paused or stopped. Pause is composed from independent reasons: initial reasons are manual and Health; future domains may add more. Generic Resume removes manual intent only and scheduling resumes only after all reasons clear. Health soft incidents may be overridden for that incident; hard actual resource exhaustion cannot. Pause blocks automatic new background work; chat, its necessary routing/consultations and task authoring remain available. Tasks authored during pause wait for resume.

**Configuration and Books evolve through one deterministic project migration mechanism.** `promptbookVersion` records the initializing/last-migrating engine version. Compare semantic versions, including numeric prereleases. An older engine uses the saved update policy to recover compatibility without downgrading the project or requiring redundant approval. A newer one applies applicable sparse steps to configuration and affected Books in order, then sets its version and commits the entire migration pass once, even with no transformation steps. No per-Book age detection or migration agent is introduced, including for an older Book later imported into a current project. Missing version means one fixed pre-versioning baseline, without structural age analysis. The first migration converts separate browser/harness settings into named [tools](cli/tools.md). See [configuration migrations](cli/configuration-migrations.md) and [first conversion](cli/tools-migration.md).

**Tools are pluggable named project resources, not additional Book entities.** Ordered `tools` records have `type`, `variant`, required `name`, optional `description` and `isEnabled` (default true). Initial types are BROWSER and HARNESS, with variant-specific typed settings. Multiple browser profiles/accounts and harness instances are supported. Different harness variants can be chosen for suitability; same-variant instances form an ordered availability/quota fallback chain. API keys are symbolic `${{ env.NAME }}` references, never committed values. Shared safe `.env` editing preserves historical assignments and adds timestamp/reason comments.

Init, CLI and dashboard use **one shared implementation** of tool types, validation, management, secret editing and persistence. Saved tool changes commit immediately and independently from active task edits. Enable/disable is primary, permanent removal secondary. In-use changes require the shared acknowledgement: tool `--force` preserves already acquired work, while the separate `ptbk stop --force` terminates the whole engine without deleting a tool. Last-enabled-type removal/disable needs its own warning/confirmation. Configuration/env/readiness refresh before tasks and during work/waits; newly available tools may serve the current task, not only the next one. See [DRY](coding-standards/shared-logic.md), [management](cli/tool-management.md) and [live tool use](cli/tool-runtime.md).

**Git history is an audit trail.** Authorized versioned operations commit by default with lowercase `ptbk: `, the responsible agent's backtick-quoted textual visual for actual agent work and applicable name correlation. System commits invent no agent or extra date. External task mutations have durable [action records](cli/action-log.md): one Markdown file per logical external action, including meaningful failed attempts under `actions/<task-file-basename>/`, versioned independently of traces and task success. Pure reads/downloads are excluded; state-changing reads are included, no-action tasks create no directory, and old tasks are not backfilled. Reconcile uncertain effects before retry; Git revert does not undo them. Commits require changes to eligible versioned files. [Storage and Git](cli/storage-and-git.md) is the entry point for storage classes and audit boundaries. Tasks, human-facing messages, tool changes, normalization and whole migration passes have their proper separate boundaries. Accepted messages/files are saved immediately; compatible conversational writes use bounded smart/debounced commits instead of one commit per message. Preserve user edits made during work to the affected files in the resulting scoped commit. No blanket staging, history rewriting or accidental secret commits. Optional `isAutoSync` defaults false and uses the repository's configured origin and started branch without duplicated JSON destination settings. Enabled sync attempts pull every 60 seconds and before logical mutations/commits, then publishes completed local work. Failed remote operations do not stop safe local work; preserve dirty state and defer unsafe integration. Real integrations use visible non-fast-forward merges, with judgment-dependent conflicts routed through ordinary Fixer. See [persistence](cli/git-persistence.md) and [synchronization](cli/git-synchronization.md).

**Wallet mediates website login without disclosing credentials to agents.** Each project engine owns a [Wallet sub-engine](cli/wallet.md), separate from Book entities and named tools. Already signed-in sessions are reused; missing authentication uses stored credentials and accessible-channel factors automatically, with protected manual entry for unavailable codes or one continuing protected Wallet workflow through verified access. Saving a password is not login success. Technical updates are autonomous; genuinely needed human input uses Wallet's own notice. Wallet mutations stay in protected storage and create no Git commits. Its ignored project-local ciphertext uses [project encryption](cli/project-encryption.md): 12 recovery words on first use, protected host automatic unlock on ordinary reboot and one restoration step on another host. Complete Wallet records are encrypted, including service/account metadata, without a plaintext index. Shared [Bitwarden import](cli/wallet-import.md) is available in Wallet and optional init with individual/all/none selection. With a usable decryption key, [new recovery words](cli/wallet-recovery.md) preserve/re-encrypt all contents; total key loss allows only a strongly warned explicitly confirmed empty reset directly in Wallet. Only Wallet credentials are encrypted now; no cryptocurrency/standard jargon appears in product UI. Browser processes [pool connections per actual profile](cli/browser.md), start with the engine and close after the last managed connection; no master/slave engine. Shared-session interference is explicitly [known and deferred](cli/known-limitations.md).

## Initialization, work and cockpit

Initialization is finite attended technical setup. After intent, destination choices are shared `<user-home>/ptbk/project/<project>` first, current directory second and a new subfolder third. OS-aware home resolution keeps the original user's scope under sudo and root's scope for a direct root launch. Global CLI use is preferred, installed/configured usable harnesses are preselected, or OpenAI Codex when none are available; real adapter checks must verify at least one selected harness. Optional Wallet setup defaults No. Blank intent retains useful noncore-agent boilerplate; nonblank intent creates relevant specialists through the normal first task. Init/start share missing-core preparation and three-way template updates, with conflicts handled by Fixer before any necessary user decision. Its first new-project input is intent, preserved verbatim with linked assets in the initialized project's `specs/_initial.md`. It prepares missing core roles and simple selected tools, saves one ordinary Expert bootstrap, commits setup by default and starts the background agenda. It does not expose advanced account-pooling choices or execute the bootstrap inline. The check-command question is removed: preserve real checks or create an explicit nonblocking informational placeholder, never claim it is actual validation. Add optional autosync setup: no asks nothing further; yes offers private-by-default GitHub publication or another supplied origin. New repositories use main; existing branch/history are preserved. Remote failure is separate from ready local work.

Init shows progress, Expert as visual guide and a brief truthful celebration, then ordinary interactive use automatically hands off (optionally through the short cancellable countdown) to the independent dashboard. `--no-dashboard`, raw/no-UI/noninteractive use returns directly; no mode waits for task completion. Ordinary interactive daemon `ptbk start` and successful `ptbk restart` likewise attach the project dashboard by default, including idempotent start of an already-running engine. Bare interactive `ptbk` offers its context-dependent first action: the focused default is init for an uninitialized directory, start for an initialized stopped project, or dashboard for an initialized project with an active engine; when any project is registered, Open global dashboard is second and technical help third; with none, help is second. About is a compact product/version/web box. Tasker creates/manages tasks; Router chooses agents and specializes one shared [MODEL](book-language/commitments/model.md) within agent/task constraints, committing the refinement with earlier values only in Git. Plugin code owns model/thinking defaults; named tools own connection/authentication/endpoint setup. Ongoing work has no shared fixed task/chat count limit and is coordinated per file in one working tree/current branch; real host/provider constraints remain visible. Independent work progresses concurrently; conflicting file edits wait. Each executing agent holds only one started unfinished task, including while waiting, but can still answer multiple chats concurrently. It handles follow-ups and discovers useful goal-driven work when no backlog remains. See [concurrency](cli/concurrency.md) and the deliberately deferred [known limitations](cli/known-limitations.md). Ordinary `--no-commit` workflows remain explicit exceptions, not permission to silently bypass required committed configuration evolution or saved tool management. `ptbk run` is removed; `ptbk start` is the ongoing work launcher.

Chatter is the **project assistant**, responsible for contextual work management and delegation, and its **spokesperson**, maintaining [project briefs](cli/project-report.md) through ordinary periodic/significant-event work independently of viewers. Root `report.book` is undated `CHAT Report` with Chatter alone, appending every timestamped brief without cleanup or overwriting. Dashboard/status immediately read only the last complete parsed message. Explicit Refresh coalesces shared generation subject to task pause and actual resource availability; Discuss creates a new ordinary `chats/` thread with the exact displayed first Chatter snapshot. Reading never generates work; see [presentation](cli/project-report-ui.md).

The project dashboard root is a responsive **no-scroll home screen** with a prominent shared full-width Promptbook/ptbk and project identity and full-width brief (lifecycle state stays in the tiles) above its compact tile grid. Operational domains include Harnesses (replacing the former Current work tile/log), System, Health, Tools, Wallet, Agents, Chats, Tasks, Usage, External activity log, History, Files, App and enabled Synchronization. Arrows move focus, marked by a double border/bold heading without changing geometry; attention is independent and may transiently blink/pulse without stealing focus. Enter opens a full dashboard page (the root grid disappears), pages may scroll, and Escape returns; root Escape exits only the viewer. Complete task views use smart current-work ordering and user-selected sorting, independently of engine scheduling. Project Book sources are editable with shared rich input, nonblocking warnings and ordinary Fixer repair. Viewing/editing share one [Book core](cli/book-viewer.md) that handles very long sources. [History](cli/history.md) reads Git messages/topology and [Files](cli/files.md) is read-only confined browsing with formatted Markdown/JSON/Book and supported images; video playback is deferred. The same tile/drill-down hierarchy continues inside Tools and Health. Details use consistent keyboard-accessible drill-down for actual execution context, named-tool management and browser diagnosis. Terminal rendering coalesces obsolete frames under hidden/slow-output conditions without losing durable events or blocking the engine. **A synchronization panel, its details and manual Synchronize now action exist only while autosync is enabled.** Browser repair and synchronization call shared engine operations; clients do not duplicate business logic. Technical detail lives on pages while significant blockers remain summarized/attention-marked on the home screen. System owns manual lifecycle controls and pause reasons; Health is only the UI over the per-engine Health sub-engine. Terminal, lightweight browser SPA and independently usable API control the same service. Dashboard/API access is loopback-only, with local client authentication and same-origin safeguards; the local address is the private transport of local clients, not a presented connection. The [App connection](app/connection.md) links each project engine to the Promptbook App and replaces the former Connection page. Git autosync remains a separate opt-in.

`ptbk dashboard --global` is a separate refreshed host-wide table of known projects, including stopped ones, across installations/versions and independent of CWD. Entries survive stop/reboot; the view stays open at zero entries and attaches to selected live engines without cd or startup. Explicit individual/bulk Start, Start paused, Stop, Force stop, Pause and Resume call shared operations. Individual/bulk removal forgets only verified stopped entries, preserving project data. `ptbk panic` confirms (or accepts `--yes`) and immediately force-stops accessible local engines and owned execution, leaving them registered and stopped now, with enabled next-boot startup paused without tasks; no soft/pause variants exist. There is no global engine. Ordinary project dashboard entry still diagnoses a missing service actionably.

Chat primarily coordinates, checks status and creates/manages tasks; substantial execution belongs to tasks, with live cards, questions and results in the originating chat through [named links](cli/chat-tasks.md). Progress collapses after the final reply to Thinking plus elapsed duration. Appended CHAT TITLE changes presentation without identity changes. Human-facing chats support multiple agents with actual authorship and question/active-invitation/main-agent routing. `@Adam` and `{Adam}` are passive references; `+@Adam` and `+{Adam}` invite/address the agent without duplicate membership. Literal examples/history replay never invite.

[Raw usage](cli/usage.md) is durable fine-grained evidence, stored separately from harness output/video and from independent historical price observations. Retain executing agent, owner, initiator, work hierarchy, actual tool/model/account, time and available token categories. Self/inclusive views must not double-count project totals. Calculate with prices valid at consumption time; later price reductions do not change earlier rates. Historical price snapshots and aggregate caches may remain ignored; no complex automatic repricing mechanism is required. The simple Usage view defaults to seven days, may remember its last grouping and visibly distinguishes subscription/API and certain/estimated/unknown data. Price version/timestamp internals stay hidden.

[Book layering](book-language/layering.md) explains progressive source evolution. New chats are implicitly open without an initial status line; status/title changes and participant joins are appended chronologically, preserving their positions and history. The last valid status/title is effective, without making every Book universally append-only.

[CHAT MESSAGE AUDIO](book-language/commitments/chat-message-audio.md) binds recorded user/agent speech as another representation of its originating message, not supplemental input or a second request. Finalized audio files are project chat assets committed with their bindings by default, independently of task traces; preserve overlap timing, actual played speech and interrupted/incomplete capture honestly.

[Local realtime voice](cli/voice-chats.md) runs in the same chat from the terminal or the local Windows/macOS app. The terminal opens a [temporary browser surface](cli/interactive-feature-bridges.md) independent of the project HTTP server. The app presents audio, controls and captions inside the chat. The common [harness voice capability](cli/harness-voice.md) initially supports native Codex/ChatGPT login. Other adapters explicitly report unsupported, and setup guidance follows actual installed-version/account readiness. Audio interruption and task cancellation remain distinct. Chat persistence, task control, Pause and Stop retain their ordinary semantics.

Chatter is the editable core default for human-led project conversation. New chat first offers Chatter (Enter) or another agent; only the latter expands all valid targets. Initial TEAM includes the other initialized roles; specialist advice and execution use normal consultation/tasks. Existing chats/questions retain their real authors. Human-facing messages persist immediately and use debounced scoped commits; task-internal consultations retain result attribution, and conversation-only consultations use scoped authoring persistence.

Logical task identity, Git/source provenance and evidence location remain distinct. Trace directories exactly match source basenames, not normalized TASK names or opaque IDs. Evidence preserves declared names, revisions, actual tool instances, available harness output/events and enabled attributable browser recording. Init saves independent trace-commit, video-ignore and recording choices; runtime, secret stores and browser sessions stay ignored regardless.

## Remote App integration

The target [version-zero App contract](app/integration.md) prioritizes App-started VPS installation/pairing, shared project init with real harness authentication, onboarding files, simple Wallet input, attributed multi-party plain-text chat, native project lifecycle and the update switch. The engine remains autonomous without clients or relay; the simple host service only discovers/launches/monitors processes and has no project/update scheduler. Central services see no readable project content or secrets. Each project engine links to the App as its own App engine through the [App connection](app/connection.md): `ptbk connect --link <code>`, a signed registration and heartbeat, and a relay tunnel per relay that carries only encrypted browser TLS, which the engine ends itself on its own origin: passkey sign-in (the first owner through `ptbk connect --setup-link`), the platform's engine API and the signed App UI, accepted by the platform's conformance suite. Existing local HTTP protections stay in force, and the local listener is never published through a tunnel.

Direct Book/forms editing, existing-CLI attachment/re-pairing, browser control, rich chat, background notifications and remote duplex media are designed for later. [Live tab control](cli/browser-tab-control.md) and [voice](cli/voice-chats.md) in the terminal and local desktop app use local connections. Terminal-in-App is the preferred service fallback for assessment, not a settled first-release implementation. Detailed task/run/chat/identity, security/release and UI contracts must be agreed with the App team; do not treat a predecessor-shaped draft API as an accepted Reborn contract.

## Current refinements

New initialization is one reversible in-memory draft through [final create-and-start confirmation](cli/initialization.md#draft-confirmation-and-project-creation), without touching/creating the target beforehand. Global harness installation/login, actual functional checks and a separate semantic project-name call may occur before that boundary; their accepted small usage stays outside project totals. At least one harness must pass; additional failures remain visible and nonfatal. A naming failure after a passed check is an unexpected error before creation. The review permits title/folder edits. Global New project reuses this same wizard with a home-only destination-step variation.

[Wallet testing](cli/wallet-testing.md) verifies one selected credential through the shared real login flow, supports protected human completion and retains only the latest redacted result/time/reason outside Git. Incomplete new credentials remain saved as unverified. Agents may inspect nonsecret metadata, use multiple supplied accounts, discover verified related service origins and retrieve accessible emailed codes themselves. Reusable additional fields are encrypted; one-time codes are not reusable records. Mobile SMS integration and Wallet-owned TOTP generation/import are future scope.

The cockpit has no standalone Results/Activity tile/page/attention. System retains operational logs, individual tasks retain results/errors, and External activity log/History retain their distinct external-effect/Git meanings. Default task views emphasize content work, mute/lower supporting system work independently of core provenance and leave scheduling unchanged. Files exposes hidden agent directories such as agents/.core while preserving protected paths; all Book view/edit surfaces share syntax highlighting.

## Live sessions and evolving task direction

[Harness sessions](cli/harness-sessions.md) separates tasks, chats, sessions, turns and processes. One task may use several sessions; the Harnesses home tile/page replaces Current work and includes idle sessions, actual execution/usage and task/chat/agent links. Common detail opens actual native attachment only where supported: deliberate watch/exclusive/shared modes, full-screen handoff, verified detach and restoration to the same detail. No copied TUI or second executor is allowed. Whole-engine Pause/Stop remains distinct from session-scoped control ownership.

[Task control](cli/task-control.md) makes Chatter responsible for carrying a contextual request through the right agent(s), retaining the real user's authority and actual outcomes. Append [TASK CHANGE](book-language/commitments/task-change.md), source provenance and typed state/schedule amendments; distinguish saved, delivered and applied per affected session. Reopen the same work with [TASK REOPEN](book-language/commitments/task-reopen.md), keeping past DONE/results. Cancellation/retirement preserves Book/history; deletion and rollback require their own intent. New fundamental work becomes a linked new task. Lifecycle, recovery, source ordering and completion checks prevent obsolete work or duplicate effects.
