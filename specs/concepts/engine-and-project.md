## Autonomous operation and minimal interruption

**The engine should accomplish authorized work as autonomously as possible and involve the user only when genuinely necessary.** Prefer existing context, routine deterministic recovery and ordinary agent/Fixer consultation over repetitive approvals or questions. Attention is an exceptional request for useful human action, not the normal steady state. With a supported running host and available resources/access, the target is sustained useful unattended operation, including a year-long agenda without routine interruptions. Completed attended initialization with required access should suffice without a later routine dashboard visit. An authorized publishing agenda adapts to service/interface changes and remains active over the year; an accounting agenda performs authorized submissions without per-send reapproval. Existing scope, accounts, spending limits and explicit review requirements still apply.

One pending question, missing credential, blocked task, failed remote sync or recoverable domain problem does **not** stop the engine. Checkpoint/release safe resources for the affected operation and continue independent eligible work; retain domain supervision/retries and responsive controls with zero viewers. Apply actual manual/Health pause and deliberate stop only under their explicit lifecycle contracts. Do not manufacture work or paid calls merely to appear busy.

Closing or signing out of the App, losing a client device, an unavailable relay or a long user absence is not cancellation of the agenda. No periodic "continue working" confirmation is required. The engine owns work, recovery and its own [updates](../cli/updates.md); the App is an optional observing/control client. These are cross-system requirements on scheduling, Wallet, updates, connections and human interaction, not just wording for the happy path. Unavailable host resources or genuinely necessary human action can still block the affected operation.

Use **one common attention mechanism** across chats, tasks, Wallet, Health, Tools and other domains. Deduplicate a still-pending condition; clear resolved items automatically. A user response clears that question's attention immediately when accepted/saved, without waiting for an agent or commit. Reading/navigation alone does not answer, and a different unresolved request can remain pending. Validate actual authority/access before resuming work; minimal interruption is not permission to assume consent or hide uncertainty.

This principle is shared by [unattended operation](../cli/autonomous-operation.md), [automatic repair](automatic-repair.md), [concurrent work](../cli/concurrency.md), [human interaction](../cli/user-interactions.md), [Wallet](../cli/wallet.md) and [dashboard attention](../cli/dashboard-layout.md#focus-and-attention-are-independent). Those are implementations of the same product behavior, not independent escalation policies.

## Engine and project evolution

A running Promptbook engine and a user's project evolve on different timelines. **Engine-defined system agents** such as `@Expert` belong to the invoked engine; their effective Book-like instructions may be internally embedded or generated. They can be comprehensive and change when that engine version changes. Expert describes the currently running Promptbook, not the version that originally initialized the project.

**Project configuration and affected Book sources** evolve through one explicit deterministic versioned migration chain. `ptbk.json.promptbookVersion` records initialization or the last successful migration to an engine version, not an independent schema counter or permanently fixed creation version. A newer engine applies applicable sparse steps and commits the whole pass once; an older engine restores compatibility through the saved update policy instead of downgrading the project or asking for redundant approval. The fixed versionless baseline and actual first conversion are defined by [configuration migrations](../cli/configuration-migrations.md), not guessed from Book contents. There is no separate per-Book version or age detector; inserting an older Book into a current project does not trigger automatic migration. A migration agent is future scope.

**Core agents** are ordinary editable project Books required by the engine and initialized only when missing. Defaults are small and comprehensible. They then belong to the project and accumulate instructions, experience and learning like other agents. Init/start share [core preparation and three-way template updates](../agents/core-agents.md#shared-preparation-and-template-updates): add missing roles, compare old/new templates with the project Book, apply unambiguous updates and send conflicts to Fixer before any necessary user decision. Preserve customized/learned content instead of freezing all templates forever. A malformed existing file is diagnosed and repaired through normal authorized work, not overwritten with a boilerplate because its engine changed.

**Other project agents** have the same Book, runtime and learning behavior; the engine simply does not require every specialist in every project. Default OPEN/CLOSED semantics apply alike. Fixer is a normal OPEN core whose initial team includes User and Expert, and whose problem-solving/consultation policy can be customized. Teacher is CLOSED by its own policy, not by being core. The cross-system [automatic repair principle](automatic-repair.md) uses this normal Fixer rather than an independent privileged learning or communication subsystem.

Project evolution preserves [user-defined anchors](anchoring.md). OPEN/CLOSED and any learning limits constrain automatic changes to meaning, including repair and template reconciliation; agents cannot authorize themselves to weaken those limits. [Engine-owned tasks](../cli/system-tasks.md) describe definition ownership, distinct from core provenance and project-relative content/system purpose.

*Illustrative analogy only:* a company's general framework may evolve centrally while its accountant learns local practice. This explains coexistence of engine evolution and project knowledge, not a new Promptbook object, service or legal guarantee.

Human questions should mainly concern project substance, a missing decision/input/authority or a genuinely necessary human action. An exhausted retry counter is not itself a reason to ask whether to continue. Use [cause-aware recovery](../cli/retries.md), keep [external-action records](../cli/action-log.md), continue independent work and automatically retire requests whose underlying problem is verifiably resolved.

The canonical [minimal-interruption knowledge base](minimal-interruption/_index.md) expands this principle with concrete examples and contextual work-purpose rules. Existing dashboard inspection/control and the operator's final say remain available independently of notifications. Ordinary technical repairs are allowed by default within effective authority unless instructions restrict them. The active-attention threshold is an actually needed human decision/input/action, not significant completion, history or autonomous repair progress.
