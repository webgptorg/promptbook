# Content judgment and changing project boundaries

[Principle](_index.md) · [Work purpose](work-purpose.md) · [Tasker](../../agents/core-agents/tasker.md)

| Project and activity | Typical purpose and reasoning |
| --- | --- |
| Accounting agenda: prepare/file VAT and pay authorized invoices | CONTENT: this is the responsibility the user delegated to this project. |
| The same accounting agenda: install a parser to read the authority's XML | SYSTEM: technical support enabling the accounting work. Usually a separate linked task rather than a new purpose for the VAT task. |
| Accounting/invoicing software product: implement a reliable XML parser | CONTENT: this technical functionality is part of the product being built. |
| Website-development project: fix the delivered web server | CONTENT when the server is part of the project's deliverable; assess the actual boundary rather than the word "server". |
| Social publishing/accounting project: build an incidental service connector/server | SYSTEM when it only enables the delegated publishing/accounting work. |
| A broad company agenda: establish and operate a business selling cookware | Tax filing can be supporting SYSTEM work relative to that project's business purpose, while it is CONTENT in a dedicated accounting project. Assess actual scope and instructions. |
| Router chooses an execution agent for another task | Usually core/SYSTEM work enabling the target's work. |
| Teacher learns a project-domain distinction from verified feedback | Can be core/CONTENT work even though Teacher is a core role. |

These are contextual examples, not permanent labels attached to technologies, job titles or every occurrence of a verb. A content task can be instrumental to a higher objective without becoming system work at the project's intended level. Leave purpose undefined when the available context does not support a useful distinction, then refine with evidence rather than ask a routine classification question.

## When content needs the operator

An agent authorized to pay routine invoices receives an unusual or suspicious invoice. The payment is technically possible, but the unresolved substantive judgment can justify asking. The same applies to a controversial publication whose acceptability is not established by project instructions. First inspect existing rules/context and useful specialist evidence; do not ask again when the relevant authorization already clearly covers the action.

This remains true if the accounting task is supporting/system work in a broader business project. Purpose influences presentation and the tendency to resolve service details autonomously; it does not make an uncertain payment safe or erase an explicit review rule. Conversely, content work does not require approval for every routine step merely because it is prominent.

The operator should guide strategy and exceptional judgments rather than approve every report, post or submission. Preserve the final human say, actual audit trail and visibility through the existing dashboard.
