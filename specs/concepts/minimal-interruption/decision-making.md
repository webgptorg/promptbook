# Autonomous decisions and genuine attention

[Principle](_index.md) · [Automatic repair](../automatic-repair.md) · [Human interaction](../../cli/user-interactions.md) · [Health](../../cli/health-sub-engine.md)

## Resolve before asking

Use the mandate, effective agent/project instructions, existing evidence, available accounts and ordinary specialist/Fixer consultation. Try useful supported alternatives and cause-aware recovery. A failed attempt, an unfamiliar format, a CAPTCHA or the end of an immediate retry budget does not establish that a human is needed. Avoid repeated equivalent attempts without new evidence and paid idle loops.

Ordinary technical configuration, dependency installation, runtime adjustment and creation of a useful connector/plugin/helper are allowed by default within existing access and authority unless effective instructions restrict them. The operator need not enumerate every such implementation step. Explicit rules, goals, spending limits and review requirements still govern; inability to obtain an OS privilege or an external permission is not permission to assume it.

Content decisions also use available instructions and context first. Ask for an actual missing consequential judgment, information or authority when necessary, rather than repeatedly reconfirming a delegated agenda. A suspicious invoice may need judgment even though the agent is technically able to send the payment. Task purpose is contextual and does not itself grant financial/publication authority or remove a genuine human dependency.

## When a method fails

First identify what the user actually needs and which constraints they specified. A search page may be optional, while the named publisher, account, date, recipient or approval can be essential. Choose a permitted alternative that still meets those constraints. Verify the result against the original assignment before recording completion.

| Situation | What the agent does | When to involve the operator |
| --- | --- | --- |
| A search engine shows a CAPTCHA while the task is to verify a public event | Leave that page. Read the original bulletin or another independent, attributable publication. Check the date, place and claim, and cite what was actually read. | The search challenge alone creates no request. |
| A specific account's export is required and its web form is gated | Use the service's documented API if the project already has the required access. Check the export belongs to the requested account and period. | If access is genuinely missing, ask once for that specific permission through the appropriate channel. |
| A required source is unavailable and the task expressly requires that source | Keep the requirement and checkpoint the affected work. Recheck when there is evidence access can change. Continue other eligible work. | Ask only if the operator can supply missing access or must decide whether to change the requirement. |
| A submission times out after the final click | Look up the acknowledgement or transaction on the service before taking further action. Keep the evidence with the task. | An uncertain result alone calls for investigation. A new payment or a change in authority requires the applicable decision. |
| First use of a private account needs a credential, or the service asks for a phone approval | Use a suitable existing session or protected Wallet credential first. Identify which required factor remains. | Ask for the unavailable credential through Wallet or for the owner's physical approval. Resume the affected step after verification. |

A known temporary outage uses the existing [retry and recovery policy](../../cli/retries.md). A stable access restriction with no authorized route remains visible on the affected task. Another identical attempt needs a reason to expect a different result.

## One attention contract

Active attention/notifications mean **a concrete decision, input or action from the human is now needed**. Apply this to every domain, not only tasks. A significant completed result, unread history, an old failure, a recoverable warning or an ongoing automatic repair is available for inspection without creating attention on that basis alone.

A useful notice identifies affected work, why autonomous resolution is insufficient, what has been tried and the smallest action needed. Missing website secrets/codes use Wallet's protected workflow. Other substantive questions retain their normal attributed conversation. Deduplicate the same unresolved condition and remove stale attention when its condition is verifiably resolved. A saved response clears its answered input immediately; completion still requires verification of the underlying access/action.

Keep [seen state separate from resolution and optional external effects](../../cli/notifications.md). A genuine chat request explicitly pings `+@User`/`+{User}`. Actually viewing that message, or explicitly marking a Wallet request seen, removes that occurrence's alert across clients without answering or unblocking work. Health retains its domain resolution/override rules. Deliberately ignoring a seen request is valid; do not issue timed reminders or replay effects suppressed during recent activity.

The [responsible agent](../../cli/notifications.md#ownership-and-continuing-relevance) owns each notice from creation through withdrawal; system/orphaned notices belong to Fixer. Responsibility continues during ordinary waiting through [progressive checks](../progressive-waiting.md), with bounded paid judgment when useful and no automatic agent checks during Pause. Resolution appends a concise explanation in the original chat instead of editing historical pings. Never cancel the user's current draft/form under their hands; announce resolution nonblockingly and allow valid input to finish.

Long lack of useful progress must be diagnosed rather than hidden by a live process. When autonomous remedies cannot restore useful work and a human action/decision is necessary, surface one current understandable problem with its impact and attempted remedies. Elapsed time or an exhausted counter alone is not a human question. Unrelated work continues wherever its prerequisites and ownership permit.

## Observe, audit and resume

The operator can always voluntarily inspect work through the existing dashboard. Keep diagnostics and outcomes even when they cause no notification. Git records versioned changes; remote state changes not inherently represented by project files use the existing [External activity log](../../cli/action-log.md), including publication of a helper application or an authorized infrastructure resize. Technical intent does not exempt an external effect from audit. Reconcile uncertain effects before retrying them.

Checkpoint the affected operation and resume the correct phase after repair or verified human action, without another generic Start/Retry prompt. Do not turn one waiting credential, task or domain into a global work stop. Actual host exhaustion, deliberate pause/stop and unsafe shared ownership retain their existing lifecycle rules.
