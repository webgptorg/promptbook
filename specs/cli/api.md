# Project service API

[Main specification](../_main.md) · [Shared runtime controls](controls.md) · [Remote access](remote-access.md)

The active project service exposes an independently usable HTTP API for inspecting and controlling its runtime. It works without opening the browser app or terminal dashboard; neither client owns the service or starts a separate queue. Keep service behavior and API responses independent of page rendering.

Start enables the local HTTP server in either process mode, binding to loopback with an automatic free port or `--port`. Report the actual address and explicit port conflicts. A managed protected tunnel is enabled by default under [remote-access policy](remote-access.md), without changing the local bind address. `--no-tunnel` leaves local HTTP only; `--no-server` disables HTTP, the browser app and the tunnel. When enabled for finite run, these belong to that invocation and must not keep it alive after completion.

Expose authenticated structured runtime state and shared controls: actual service engine version, project identity, agent/task/harness and known model/effort, phase, queue/task details, results/statistics, waits, blockers, errors, chats (unread and waiting-for-user counts), links and effective settings, including commit mode. Include state freshness, local address and remote provider/address/health for the [shared view](status-view.md); clients must not guess ports or mistake local availability for remote readiness. Ordinary state does not contain pairing secrets or device/API credentials.

Chats expose their **name, participants, actual message authors, status, timestamp, history and task links** so every client can make the agent-authored waiting conversation primary. Support authenticated list/new/open/append-message/answer operations using the same durable Book sources; selecting the chat uses its **normalized name**, not a generated chat ID. A user answer is a committed message, not a runtime-only request resolution. Provide idempotent mutation/revision checks to prevent duplicate messages from stale clients or reconnect. Distinguish automatic assignment/discovery from waiting for the user. Expose canonical agent identities and observed activity for the shared [visual identity](../agents/visual-identity.md); rendering differences must not change attribution or invent execution states.

New task/chat creation uses the same [generated-name policy](generated-names.md) as CLI and dashboards: persist a typed opening commitment, proactively include creation date/time in the readable name, and resolve normalized collisions before returning success. Return the final full name and its reference/path; do not make clients append timestamps or address a pre-disambiguation title. A retried creation returns/reconciles the original prepared entity rather than allocating another name. Reading, opening and appending to an existing entity retain its name; a missing date in an otherwise valid Book is not invalid API data.

Support the same applicable actions as the dashboards, including pause/resume, skipping a pacing/backoff wait, graceful stop, chat entry/answers and allowed settings changes. Report outcomes and whether changes are active, deferred or require restart. Explicitly saving versioned defaults uses [automatic operation persistence](git-persistence.md); temporary/runtime-only changes do not manufacture commits. A requested action or save is not completed before application and any required commit.

Clients obtain fresh state and observe changes made through other channels. Inspection is read-only. Mutations obey the same ownership, source revision, task, configuration and recovery rules. Runtime views need neither HTML forms nor server-rendered fragments. Serve the SPA/assets and its API through the same local or public origin using compatible URLs and live updates; an SSE-only implementation is not sufficient for a provider that does not support SSE.

Protect project data as well as mutations before exposing a tunnel. Unauthenticated clients get only minimal pairing/app-shell information, never project content or control authority. Use the project-scoped pairing/session and direct-client authorization contract from [remote access](remote-access.md). Reject unauthorized cross-origin requests, stale edits, invalid input and access outside the project. Neither an opaque hostname, forwarded headers nor apparent localhost origin is authorization. Never expose secrets, browser-profile contents or unredacted diagnostic data; prevent shared caching of authenticated data and credentials. Applying an already-resolved answer or posting a duplicate accepted message twice is forbidden. Never announce a message as persisted before its scoped Git commit (or explicit no-commit outcome).

Client or tunnel failures do not stop a daemon, duplicate tasks or reset state. The [browser dashboard](dashboard.md) remains a lightweight consumer served at the same server's root. See [channels](channels.md), [user interactions](user-interactions.md) and [process modes](process-modes.md).
