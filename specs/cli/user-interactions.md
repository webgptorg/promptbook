# Human-directed conversations and exceptional decisions

[Chats](chats.md) · [Unattended operation](autonomous-operation.md) · [Chat presentation](chat-ui.md)

Ordinary questions, decisions and nonsecret human-only actions are **messages from a concrete agent in a durable chat with @User**. Website username/password input is the explicit exception: [Wallet](wallet.md) owns a protected secret-input action, while chat can carry only its nonsecret reason/link/outcome. Never ask for the credential in chat. Challenges are handled autonomously when supported; only a genuinely human-only step requires actual human action with secret-safe entry. Technical Wallet updates do not receive a blanket confirmation requirement; any necessary Wallet action/decision belongs to its own protected notice rather than secret-entry chat. Ordinary nonsecret questions are not a second project entity called Request or an anonymous engine alert; they use the same Book messages, history and persistence as user-initiated chat. Wallet's protected action is the explicit secret-entry exception, not a new Book kind. TEAM @User, startup/access problems and exceptional recovery conditions can all initiate or continue an appropriate agent→User conversation. The agent author and affected task/project condition must be explicit.

Human involvement follows the [engine's minimal-interruption principle](../concepts/engine-and-project.md#autonomous-operation-and-minimal-interruption) and must remain exceptional. One pending action blocks only affected work, not the engine; safe independent work and supervision continue. Use authorized project context, ordinary task instructions and bounded automatic recovery rather than routine per-action reapproval. Do not start duplicate chats for the same still-unresolved condition, silently presume assent, or claim answering one question cures an unchecked technical prerequisite. A chat can contain further clarification or explanation before the human makes the required decision.

## Attention and state

Waiting-for-user chats are the **highest-priority** dashboard attention content, with pending count, affected work, agent author, reason and a direct open-chat action visible without scrolling. Unread chats are also shown distinctly, but unread alone does not mean blocked. List **all chats** through an explicit view; no special Fixer category or separate request pane is necessary. Narrow screens retain actionable content above routine queue and activity. Opening/read markers never resolve the underlying condition or commit a synthetic answer.

Status snapshots and raw output give a usable chat name/ref and `ptbk chat` / `ptbk answer` guidance without waiting on stdin. Terminal `A` opens the relevant existing conversation; browser and authenticated API use the same messages and action state. Live updates do not steal focus or discard drafts. Each accepted answer is saved once and immediately clears that question's attention before agent acceptance/Git batching. Other pending questions retain their state.

## Waiting tasks and recovery

When a task requires actual human assistance, reuse its originating/designated chat under [chat/task relationships](chat-tasks.md), adding the executing agent before it speaks; create another only if no suitable chat exists. Store named task↔chat references and its durable checkpoint, including the exact question, offered options, prior authorized effects and resume point. Return from the provider turn promptly; human waiting must not tie up an MCP call until timeout. The task remains unfinished without counting a failure or launching duplicate provider turns. Safe independent work may proceed only after releasing ownership; shared resource conflicts are explicitly reported.

Only a real applicable reply or completed human action permits continuation. Reject stale/double answers, distinguish reject/cancel/unavailable from approve, and validate the state of required external access after a claimed login. After restart, retain the same chat and checkpoint; answering through any channel is reflected in all channels, and the original task resumes automatically when safe. A task must still pass its normal checks before completion. Do not assume a message is an approval merely because it exists.

When an agent provides predefined answer choices, terminal/browser render them as selectable controls. Values are unique nonempty human-readable strings, at most 50 options of at most 1000 characters each; reject malformed duplicate/whitespace-only choices instead of trimming or silently merging. Open-ended prompts use the rich composer; noninteractive API/CLI uses explicit response values. Chat history and message semantics must preserve these choices, without turning choice labels into entity IDs.

## Compatibility and acceptance

Upgrade old pending request records into durable chats without losing evidence, agent origin or wait status, and without repeated questions on restart. `ptbk answer` remains an alias/compatibility path to the selected waiting chat, not a parallel mutable request store. An answered chat no longer appears as awaiting attention, but remains browsable with history and task relationships.

Exercise multiple waiting chats, a multi-turn clarification, reconnect and process restart, stale/double answers, rejected decisions and a task safely releasing/reclaiming execution. Every human-facing message is saved immediately, attributed to its sender and included in a bounded debounced Git batch. A task with an agent↔agent TEAM consultation retains that internal conversation in its task result commit, not in human attention.
