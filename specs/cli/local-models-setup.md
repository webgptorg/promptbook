# Local model setup and management

[Main specification](../_main.md) · [Inference runtimes](inference-runtimes.md) · [Initialization](initialization.md) · [Tool management](tool-management.md) · [MODEL](../book-language/commitments/model.md)

Provide one **Local models** choice alongside the existing featured harness choices and More. It is a resource/setup category, not a new harness variant. Users may select Local models alone or together with OpenAI Codex, Claude Code, Qwen Code or other supported integrations. The ordinary path asks only about using local models and a suitable download, not the harness/protocol underneath. Advanced details expose runtime, model and compatible harness selection without making them mandatory questions.

The same workflow is available after initialization as **Tools → Local models → Add local models** and `ptbk tool setup-local`. It works for stopped and running engines, without another init or restart. All presentations use one engine-owned setup state machine and the same runtime/harness domain operations, including staged persistence. A remote client always prepares the engine host, never its own device. Expose new remote App fields/operations only through its agreed versioned contract, not an invented client-only implementation.

## Supported starting combinations

The first automatic-install baseline is **Codex CLI + Ollama + a verified suitable local model**. Codex supplies the existing agent/session integration; no cloud login is required for this connection. Supporting an existing compatible LM Studio service/daemon uses the same runtime abstraction. Automatic LM Studio/llmster installation and additional harness/runtime pairs extend that contract as their platform installers and end-to-end capabilities are verified; do not label them one-click ready in advance.

Publish the actual tested OS/architecture/runtime/harness/model/quantization matrix, including CLI-supported Windows, macOS and Linux/VPS paths where available. No GUI-only installer may become a hidden requirement for supported SSH/CLI setup. Recommendations select from verified combinations for the actual installed versions, not an assertion that every GLM or OpenAI-compatible model works through every harness. The matrix/recommendation catalog is extensible and refreshable; cached known data can support already prepared offline operation.

## One setup journey

1. **Discover.** Inspect the engine user's OS/architecture, available RAM, GPU/VRAM/acceleration, free disk, service permissions, existing runtime/model stores, harness executables and active consumers. Distinguish CPU-only support, unsupported hardware and unknown capacity. Readiness comes from the actual service-user environment, not only the initiating shell.
2. **Recommend.** Offer a verified model/runtime/harness combination suited to the host, reusing healthy installations/models first. Show model identity/quantization, known download size, expected disk and memory/context needs and applicable license/terms information. Explain meaningful capacity or speed limitations without fabricated benchmarks. Account for context and concurrent consumers as well as weight size. Offer an explicitly selected smaller supported model or a clear incompatibility when necessary; never silently use cloud inference.
3. **Prepare.** The accepted local setup/download choice authorizes its stated prerequisites. Install only missing compatible components from supported distribution sources, with the adapter's supported integrity/version checks. Prefer ordinary-user installation and request native administrator consent only when actually required. Preserve working shared services, stores, logins, project files and unrelated shell settings. Reuse the selected harness's global executable, with safe coordinated update when genuinely required; do not install one duplicate per project.
4. **Download/load.** Show actual progress, size where known, recoverable failures and cancellation/resume availability. Reuse already verified weights; interrupted or corrupt data is not an installed model. Coalesce simultaneous requests from several engines. Load the selected model and report real service/memory failures without changing its identity, quantization or context requirements unnoticed.
5. **Connect/test.** Prepare a separately named local harness connection and runtime reference. Select the provider and credential-free mode for this invocation, with no global harness reconfiguration. Verify the bounded functional path below, then recheck the settings/executable/endpoint the daemon will actually use. Preparing a connection is not changing an existing subscription connection.
6. **Save/use.** New init carries these choices through its normal final review and setup transaction; later Add local models saves the runtime/harness additions together in one scoped management commit. Mark readiness only from actual results. Make the new route available to compatible work immediately. Return the concrete configured runtime, model and harness connection, honest pending steps and the route to agent MODEL settings.

Use discovered/recommended values as editable selections, not fixed examples or extra per-tool model defaults. Retain draft choices and completed prerequisites on Back, retry and cancellation. Noninteractive callers supply equivalent local/runtime/model/download decisions, get structured progress/outcomes and never wait for hidden login, installer or download questions. Generic read/list/show operations never trigger setup.

## Initialization and bootstrap

Selecting only Local models must prepare its necessary harness automatically, without implicitly selecting that harness's hosted subscription route. Explicit local-only selection overrides ordinary Codex preselection; do not reinsert a cloud route on re-entry. Selecting Local models plus Codex subscription produces two independent named connections sharing the executable. Other selected integrations retain their ordinary supported authentication. Setup state shows each selected path separately.

Pass the prepared local route/model into the earliest functional check and project-name generation, then Router's concrete bootstrap MODEL. With only local execution selected, ordinary core agents, chat, task and TEAM paths must all be satisfiable without cloud credentials or official-provider defaults. Do not create an unconfigured cloud tool to repair bootstrap. Mixed selection retains normal first-suitable-tested-connection order for Router; installing local models alone does not change its existing Book or every agent's requirements.

Run all preparatory checks in disposable non-project contexts before final creation. No target directory, Books, .env, project-local store or task is written before init's final confirmation. Shared runtime/harness installation and model downloads may already have happened; clearly state cancellation does not roll those host prerequisites back. At least one actual working selected execution path is required. Additional failures stay visible under init's existing continuation rules; a working cloud route must never cause a failed local setup to appear successful.

## Existing projects and compatibility

Adding local support is additive. Preserve existing names/order, explicit disabled records, native subscriptions, API routes, secrets, Router customization and saved agent/task/chat MODEL. Reuse or create distinct names without duplicates on retry. Detect requirements that currently exclude the new local path and explain where to edit them; do not silently rewrite a customized agent, reroute an existing chat or relax an explicit model requirement. Agent/source editing uses ordinary MODEL authoring, including combined local-plus-model constraints.

Adding support and deliberately restricting selected agents/tasks to local inference are separate saved operations. Whole-project local model operation is achievable by deliberately choosing compatible local execution for routing/helpers and disabling unneeded hosted routes; it is not an automatic side effect of Add local models. Show model-inference scope separately from optional network tools, speech and synchronization.

Use the ordinary versioned migration mechanism for any schema expansion when implemented, without selecting a release number in this specification. Existing explicit endpoints and authentication remain preserved. A legacy `baseUrl: LOCAL` without an unambiguous runtime binding gets an actionable setup/compatibility diagnostic; migration cannot guess a runtime, change account mode, install software, download a model or opt into local-only execution. Ordinary inspection/migration never triggers an interactive installer. Unaffected hosted tools remain usable.

## Bounded functional verification

The local setup check goes beyond PONG. In a disposable fixture, verify a real model response, a harmless tool call, the shared MCP path, permitted scratch-file work, enforceable read-only behavior and session continuation through the selected harness/runtime/model combination. No fixture may touch project/application files, an outside account or the user's desktop. Record actual supported/failed/unknown outcomes and available usage with redacted diagnostics. Reuse prior capability evidence where still valid, but do not skip the existing required real response check or use a different hosted route for it.

End-to-end acceptance after creation also exercises ordinary chat, a task, nested TEAM advice, pause/recovery and restart. These are acceptance requirements for advertising the combination, not extra project bootstrap tasks executed inline by init. An adapter without enforceable read-only chat/consultation cannot be the complete local-only setup even if it can write a task file. A changed model/runtime/harness version or capability invalidates affected evidence. Voice, images/screenshots and native interactive attachment require their own verified support, rather than being inferred from text/tool success.

## Management presentation and operation boundaries

Tools has a distinct Local models category/page, available even before a runtime is configured. Its ordinary entry is Add local models. Show compact runtime health and model availability; detail shows installed/available models, sizes, actual service/runtime/harness associations, loaded/busy state, hardware/capacity estimates, shared consumers, diagnostics and supported actions. Keep harness implementation choices in advanced details. Harnesses/session pages still show actual local/hosted connection attribution.

Offer download with progress/cancel/resume, load/unload, model removal, diagnostics, supported service start/stop/restart, update and uninstall through shared operations. Separate **Disable/remove this project's runtime reference** from **Remove model/uninstall shared runtime on this computer**. Explain and revalidate the latter's impact on other engines/consumers, refuse/defer unsafe maintenance and retain existing owner authority. A project force-stop is not a host-wide service kill. Weights/process/download changes stay outside project Git; configuration/Book edits retain their own scoped commits. No-op inspection creates neither a commit nor an inference request.

UI/CLI show honest stages: discovering, needs installation, downloading, loading, verifying, ready, waiting for capacity, unavailable, failed or cancelled as operation/resource observations, not extra engine lifecycle states. A running mixed engine can continue hosted work during local preparation or failure. Cleanup after cancellation never uninstalls healthy reused components or deletes weights another project uses.
