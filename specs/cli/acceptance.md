# Acceptance scenarios

[Main specification](../_main.md)

These are verifiable product outcomes, not an implementation plan or evidence of completed tests. Exercise common behavior with local fixture projects and deterministic substitutes; paid provider checks are separate and explicit. View-specific specifications also define their own observable acceptance outcomes.

## Installation and startup

- **S01:** Global `ptbk` and project-local `npx ptbk` work outside this repository. Two projects use different versions, and their daemons and Experts use the correct installation after restart.
- **S02:** Repeating init with unchanged choices and satisfied prerequisites preserves source exactly and creates no empty commit or duplicate starter task. Basic initialization saves but never unexpectedly executes the first task. Requested fresh-project agenda creation performs complete setup, materializes Expert's first task and begins the agenda without an Expert project file or a duplicate generic starter.
- **S03:** Plain start creates one daemon with persistence, a free localhost port and a scannable QR code for the actual URL in pretty terminal output, renders one outcome and exits without attaching a dashboard. No-server/no-QR and an explicit port behave as advertised; a port conflict is not reported as success. Bare `ptbk` shows help/version without starting or prompting.
- **S04:** Start/stop/restart/status/show target the correct project and report once. Repeated/concurrent starts do not duplicate it, attach a dashboard or control an unrelated PID. Status/show never start work; an intentional stop remains stopped after reboot.
- **S05:** Verify daemon reboot/crash recovery on Linux, macOS and Windows. No-persist disables automatic restart but retains state. `start --raw` remains a one-shot daemon launch; `start --foreground --raw` stays foreground with plain events. Explicit foreground execution never silently becomes a daemon; unsupported persistence prerequisites are reported.
- **S06:** After successful init, plain start in unchanged conditions begins real work without setup prompts, extra flags, manual assignment or a Run action. An assigned task executes; a task without an agent first runs Manager and then its target in the same session. An empty backlog with due discovery invokes ordinary goal-bearing agents and executes useful generated work. No dashboard client is required.
- **S07:** The official **Check ptbk** workflow passes on Node 22/24 across Linux, macOS and Windows for the accepted source. An authorized **Publish ptbk** release validates its exact tag through that matrix, publishes and verifies the package, and finishes successfully. Failed validation blocks publication and remains visible; code/test fixes use a new immutable release tag. See [GitHub Actions checks and publication](releasing.md).

## Initialization, configuration and maintenance

- **I01:** With dependencies available and no newer engine update, choosing the current empty folder, blank intent and at least one usable harness creates a sample project with real validation and an unfinished runnable first task. It installs the running version locally in dependencies and commits setup without a model call. Repeating satisfied setup is a no-op, including after starter completion or archiving.
- **I02:** Existing files, Git history/current branch, staging, customized agents/settings and a declared devDependency survive init. Existing projects skip the intent question. Partially initialized projects and newer-engine additions receive only missing required setup; unrelated changes never enter a setup commit.
- **I03:** Start over partial setup offers the same initializer for that selected folder and rechecks readiness before execution. Ready projects bypass it. Raw/noninteractive use never launches hidden setup/login prompts and identifies missing decisions or prerequisites.
- **I04:** Creating a child inside Git offers back, an ignored independent repository or a real submodule. Back changes neither project; ignored-child and submodule metadata are correct and repeatable. Child commits and parent changes stay separate; no invented remote, accidental parent commit or unrelated index changes occur.
- **I05:** Both global invocations and parent-local invocations creating a child offer destination-local dependencies by default. They install the exact running version, not latest. Existing local dependencies/devDependencies are preserved; selecting global does not silently add a local copy or claim a parent-local executable is global.
- **I06:** An outdated invoked engine makes self-update the first init question, defaulting to yes. No retains the running version; yes updates the correct local/global installation and exits with a rerun instruction before target setup. Offline checks and update failures are honest; noninteractive use never silently accepts an update.
- **I07:** Built-in defaults, legacy environment fallbacks, partial `ptbk.json` and explicit flags resolve in the documented order, including explicit false/empty values and relative paths. Flags/live temporary changes do not rewrite saved defaults; credentials and runtime state never enter the JSON.
- **I08:** A catalog of hundreds initially shows only featured names and More, with all integrations reachable. Selecting one harness configures only that harness; an existing authenticated global installation is reused. A supported/installed but unselected harness is not routed to or updated. Core wizard/runtime/update behavior works through the same plugin contract.
- **I09:** One outdated selected harness offers yes/no; several offer keep, update all outdated selected, or choose individually. Current/unselected harnesses are untouched. Start automatically maintains enabled harnesses by default, honors disabling overrides and avoids updating an active shared invocation. Failures preserve a usable compatible version or visibly block affected work.
- **I10:** Select two harnesses, one already healthy and one requiring login/setup. Init reports ready only after both are usable and the saved check and its prerequisites are configured. An opened login window is not completion. Cancelled login, no usable harness, deferred validation, unresolved scripts/dependencies or failed setup commit yields explicit incomplete setup, not a successful start recommendation. Resume reuses completed work.
- **I11:** The first test task has a real project-local outcome, not a disabled template or fake completion. Start uses normal harness execution, checks, completion and commit; failing checks cannot be stamped done. Init itself neither executes project checks nor claims they passed. Existing project validation and user tasks remain intact.

## Agents, language and assignment

- **A01:** Case, diacritics, separators, camel case and nested/hidden paths resolve agents consistently. Normalized collisions and reserved names are rejected with locations. Hidden agents are referenceable but not ordinary automatic work candidates.
- **A02:** Default inheritance reaches Adam; custom ancestors are allowed when the chain terminates. FROM cycles fail. Void/Null/0 ends inheritance and is a TEAM no-op; User fails in FROM and creates a request in TEAM; Expert works in both.
- **A03:** Reciprocal TEAM relationships are valid, consultations are bounded and the project still has one active task. Advisors receive their own instructions and cannot exceed task authority.
- **A04:** Start discovers enabled harnesses' global installations, authentication and models. Missing all usable enabled harnesses invokes setup or gives an unattended diagnostic. An otherwise actionable unassigned task automatically creates one checked Manager prerequisite before target execution, with a visible relationship and direct authorized bootstrap. It neither needs manual assignment nor recursively assigns itself. Explicit requirements and paid-account restrictions remain intact; retries/restart do not duplicate assignment work.
- **A05:** Implicit/explicit OPEN produces one Teacher follow-up; limited OPEN is respected. CLOSED prevents learning, including pending learning work. Teacher is customizable but must be CLOSED, and non-agents are not rewritten as local Books.
- **A06:** Agent-name-first and TASK-title-first Books are distinct. Multiline prose and fenced commitment-looking examples survive edits. Every documented commitment and alias has its declared meaning; malformed controls never silently activate work.

## Tasks and persistence

- **T01:** Duplicate task titles are valid; stable references distinguish them. Numeric/textual priority, prerequisites, parents, unavailable assignments and time constraints produce the same explanations in list, preview, controls and execution.
- **T02:** Each accepted task yields one commit containing its changes, formatter/check changes, dated TASK DONE and newly created follow-ups. Commit subject/body correspond to the assignment. Teacher's subsequent work has its own commit. No failed check is stamped complete.
- **T03:** Run is finite and uses one configuration; start operates indefinitely. At most one project task is active across interfaces and service commands. Future high-priority work does not block ready work or trigger goal enquiry.
- **T04:** On start or queue completion with no unfinished present or future tasks and no active cooldown, goal enquiry begins automatically as ordinary checked work. Useful generated tasks run without a new start or manual Run action. An enquiry may create future work or no work. Cooldowns survive restart; supporting agents, unavailable goals and empty results do not cause an unbounded generation loop. Legitimate waits have visible reasons, not invented progress.
- **T05:** Earliest-start boundaries, explicit offsets and ambiguous local times are respected. Recurrence preserves anchors and history, coalesces downtime, never overlaps and runs at most one occurrence per finite invocation.
- **T06:** Interrupt before/during checks, completion, commit and push. Safe recovery resumes the correct phase without duplicate execution/commits; uncertainty leaves the supervisor inspectable. Unrelated edits, staged content, hooks and signing are respected.
- **T07:** Commit/push failure never reruns successful model work. Full/partial reverts and changed dependencies are reconciled, including external effects. Worktree integration preserves the single task commit or keeps an unintegrated result safely.
- **T08:** Markdown states, sections, priorities and selectors remain supported. Conversion preserves payload, assets, meaning and known timestamps without making two copies runnable or inventing missing dates. Repeating conversion is safe.

## Controls, access and evidence

- **U01:** Attached/foreground terminal dashboards, browser SPA and direct API clients show and control one process and its actual engine version. Pause, wait skipping, settings changes and answers synchronize; startup-only settings and changes waiting for a safe boundary are explicit. Closing an attached terminal or browser client never stops the service; an explicit stop control does.
- **U02:** TEAM User, system confirmations and browser login requests share a durable request mechanism without being conflated. Interactive input, daemon answer, page and API can respond once; the CLI answer path works without HTTP. Raw mode never waits invisibly on stdin.
- **U03:** One project browser supports an ignored isolated profile by default, another/shared agent profile or an explicit user profile, each with independent headless/headful selection. JSON defaults and temporary CLI overrides work without resetting sessions or losing data. Competing profile ownership is rejected; a headless host never pretends to display a window.
- **U04:** Harness native authentication and browser website sessions remain independent: changing a browser profile does not log out/reinitialize a harness. No password database, key or session data appears in Git, traces or API output. External content cannot become authority to change rules; localhost requests do not bypass authorization.
- **U05:** Read-only services work offline without mutation, initialization, updates or paid calls. Plan cannot implement or delegate writes; fix does not run backlog work; verify remains human review.
- **U06:** Logs, usage and status describe observed outcomes, with unknown data and truncation explicit. Teacher uses only exposed evidence. Low disk, unavailable login, quota and repeated failures preserve work and keep a running daemon controllable.
- **U07:** Init/add use bounded step-by-step wizards; dashboard and explicit foreground start/run use a stable live execution view showing current agent/task/harness, queue, waits and errors. Dashboard/start never promise an overall finish time; run ends with its queue outcome. Add reuses supplied inputs, confirms before saving and creates no task on cancellation, with no model call or task execution. Editing, multiline paste, keyboard/pointer interaction and resize preserve input without log corruption or accidental submission.
- **U08:** Bare/help/about, wizard headers and runtime dashboards show the invoked/running engine version, including when another installed version or a newer release exists. Help remains structured and readable in a narrow terminal or redirected output, without harness configuration dumps or setup side effects.
- **U09:** Failures before, during and after task execution explain the failed phase, effect and next action, with actual redacted diagnostic evidence and versions. Trace-storage failure is explicit, with available stderr diagnostics, not a fictitious saved path. Commit/push failures do not repeat successful model work.
- **U10:** Init's Current directory/New subfolder step is a visible picker: Enter accepts the default and arrow keys then Enter choose a new subfolder without typing a choice label. Every other predefined wizard/runtime answer is selectable, including yes/no, local/global, browser choices and update decisions. Harness checkboxes support Space toggles, Enter confirmation, one/several/no selections and selectable More/paging actions; selected items survive browsing, validation, logs and narrow-terminal resize. Esc never applies an unconfirmed selection. Runtime request choices are selectable in both terminal and page, while freeform fields and unattended CLI/API values retain their existing meaning.
- **U11:** A suitable terminal defaults to a coherent rich UI with semantic color, panels/status summaries and usable controls, not merely colored logs. Lifecycle commands render one pretty result and return. Raw/redirected output contains no color, decoration, cursor controls, QR code or hidden prompts while preserving meaningful results. Narrow terminals and suppressed color do not lose information or controls.
- **U12:** `ptbk dashboard --path <project>` attaches to the existing correct service and shows live state without another worker. Opening a second client or reconnecting does not duplicate work. Q/Ctrl+C closes only the client; explicit service stop remains distinct. Missing/stopped/unreachable services have truthful diagnostics; raw dashboard is continuous plain observation, while status/show remain snapshots.
- **U13:** `/` serves a lightweight JavaScript SPA whose live data and controls use the local API, without server-rendered runtime views or page reloads. Direct API status/control works with no browser open. Terminal, browser and API actions share outcomes and safety rules; refresh, client failure and stale/unauthorized requests neither reset the service nor bypass authorization or apply an answer twice.
- **U14:** Bare `ptbk`, `ptbk help` and `ptbk --help` show the top-level overview. `ptbk init --help`, `ptbk init help` and `ptbk help init` show only init; start/dashboard/add and aliases follow the same rule, as do supported nested subcommands. Pretty and raw retain the same relevant options/defaults/examples without unrelated command dumps. Scoped help works offline without setup, required command inputs or a running service and never executes the command; invalid paths and usage errors identify the relevant scope instead of silently falling back to global help.
