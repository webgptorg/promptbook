# Acceptance scenarios

[Main specification](../_main.md)

These are verifiable product outcomes, not an implementation plan or evidence of completed tests. Exercise common behavior with local fixture projects and deterministic substitutes; paid provider checks are separate and explicit. Topic-specific specifications also define focused acceptance outcomes. Unless an explicit exception is being exercised, scenarios use default automatic commits; [uncommitted mode](git-persistence.md#explicit-uncommitted-mode) is tested separately.

## Installation and startup

- **S01:** Global `ptbk` and project-local `npx ptbk` work outside this repository. Two projects use different versions, and their daemons and Experts use the correct installation after restart.
- **S02:** Successful init saves technical setup, the original initial specification and one ordinary Expert task, then automatically starts the background agenda. It does not execute Expert inside the initializer, create an Expert project file or add a duplicate generic starter. Repeating satisfied initialization preserves source, creates no empty commit or duplicate task, and reuses an existing service without resetting it.
- **S03:** Plain start creates one daemon with persistence and a free loopback HTTP port, attempts the default protected remote tunnel, renders one status snapshot and exits without attaching a dashboard. With remote access ready, the primary URL/pairing QR works from another network; a failed tunnel is visibly degraded rather than a false localhost mobile-access claim. No-server/no-tunnel/no-QR and an explicit port behave as advertised; a port conflict is not reported as success. Bare `ptbk` shows help/version without starting or prompting.
- **S04:** Start/pause/resume/stop/restart/status/show target the correct project and report once, distinguishing an accepted pending request from completion. Repeated/concurrent starts do not duplicate it, attach a dashboard, cancel deliberate pause/stop intent or control an unrelated PID. Status/show never start work; an intentional completed stop remains stopped after reboot until an authorized start, including a subsequent explicit init's start operation.
- **S05:** Verify daemon reboot/crash recovery on Linux, macOS and Windows. No-persist disables automatic restart but retains state. `start --raw` remains a one-shot daemon launch; `start --foreground --raw` stays foreground with plain events. Explicit foreground execution never silently becomes a daemon; unsupported persistence prerequisites are reported.
- **S06:** Successful init begins real work automatically without a separate start, setup prompt, manual assignment, open dashboard or Run action. A later plain start reuses that service. After an intentional stop, explicit start resumes ordinary processing. An assigned task executes; an unassigned task runs Manager then its target. An empty backlog with due discovery produces and executes useful work without an observing client.
- **S07:** The official **Check ptbk** workflow passes on Node 22/24 across Linux, macOS and Windows for the accepted source. An authorized **Publish ptbk** release validates its exact tag through that matrix, publishes and verifies the package, and finishes successfully. Both workflows must pass for release acceptance; a failed required platform job or skipped publication is unsuccessful. Failed validation blocks publication and remains visible; code/test fixes use a new immutable release tag. See [GitHub Actions checks and publication](releasing.md).

## Initialization, configuration and maintenance

- **I01:** With dependencies available and no newer engine update, the first input is project intent. Blank input, a current empty destination and at least one usable harness produce a useful skeleton with real validation, a preserved blank `specs/_initial.md` and one unfinished Expert readiness task. Technical setup installs the running version locally in dependencies and commits without model work; its automatic start executes the task normally. Repeating satisfied setup is a file no-op, including after task completion or archiving.
- **I02:** Existing files, Git history/current branch, staging, customized agents/settings and a declared devDependency survive init. Reinitialization reuses recorded intent without reauthoring the project's purpose. Partially initialized projects and newer-engine additions receive only missing required setup; unrelated changes never enter a setup commit, and existing initial specifications/assets are not overwritten.
- **I03:** Start over partial setup offers the same initializer for that selected folder and rechecks readiness before execution. Ready projects bypass it. Its handoff creates only one service, without recursive init/start. Raw/noninteractive use never launches hidden setup/login prompts and identifies missing decisions or prerequisites.
- **I04:** Creating a child inside Git offers back, an ignored independent repository or a real submodule. Back changes neither project; ignored-child and submodule metadata are correct and repeatable. Child commits and parent changes stay separate; no invented remote, accidental parent commit or unrelated index changes occur.
- **I05:** Both global invocations and parent-local invocations creating a child offer destination-local dependencies by default. They install the exact running version, not latest. Existing local dependencies/devDependencies are preserved; selecting global does not silently add a local copy or claim a parent-local executable is global.
- **I06:** An outdated invoked engine offers an early self-update after the new-project intent field, defaulting to yes. No retains the running version; yes updates the correct local/global installation and exits before target setup with a rerun instruction and recoverable intent/attachments. Offline checks and update failures are honest; noninteractive use never silently accepts an update. Rerun does not require repasting the draft.
- **I07:** Built-in defaults, legacy environment fallbacks, partial `ptbk.json` and explicit flags resolve in the documented order, including explicit false/empty values and relative paths. Flags/live temporary changes do not rewrite saved defaults; credentials and runtime state never enter the JSON. Trace settings and init-to-service overrides follow the same precedence.
- **I08:** A catalog of hundreds initially shows only featured names and More, with all integrations reachable. Selecting one harness configures only that harness; an existing authenticated global installation is reused. A supported/installed but unselected harness is not routed to or updated. Core wizard/runtime/update behavior works through the same plugin contract.
- **I09:** One outdated selected harness offers yes/no; several offer keep, update all outdated selected, or choose individually. Current/unselected harnesses are untouched. Start automatically maintains enabled harnesses by default, honors disabling overrides and avoids updating an active shared invocation. Failures preserve a usable compatible version or visibly block affected work.
- **I10:** Select two harnesses, one already healthy and one requiring login/setup. Init proceeds to automatic start only after both are usable and the saved check and prerequisites are configured. An opened login window is not completion. Cancelled login, no usable harness, deferred validation, unresolved dependencies or failed setup commit yields explicit incomplete setup without starting work. Failed service launch after setup is separately labeled and preserves the queued task; resume reuses completed work.
- **I11:** The first task is explicitly assigned to Expert and links to the initial specification from its actual task-source location. It transforms project content rather than generating a replacement for the user's original input. The daemon applies ordinary execution, checks, task traces, completion and result commit, with normal follow-ups. Failing checks cannot be stamped done. Init neither executes project checks itself nor claims they passed; existing validation and user tasks remain intact.
- **I12:** With a globally installed Codex reporting `Logged in using ChatGPT`, valid saved defaults and other prerequisites satisfied, technical init accepts readiness without another login, API key, `--allow-credits` or model probe, even when exec/app-server lacks credit-control flags. Subsequent automatic execution, TEAM and planning reuse that account. Present API keys do not override it; signed-out API execution still needs explicit API opt-in. Native quota/credit failures remain quota outcomes without a paid fallback or a false claim that ptbk disabled provider-side credits.
- **I13:** Launch a project with a healthy globally installed Codex on a custom/version-manager PATH and native login store. Resume its saved worker under an OS-manager environment lacking those locations: it still detects that same account without a login or model probe. Missing-harness and recovery blockers remain labeled as such throughout recheck delays, even after answering their action request. Their actual reason, next action and recheck time are visible in terminal/browser/API; Skip wait cannot bypass them. Older saved workers remain compatible through the pinned Node global bin fallback.
- **I14:** A genuine User clarification starts one named agent-authored chat linked to its waiting task, ends the provider turn promptly and checkpoints without retries or another model call. Restart preserves the exact chat/question and task context. Independent work can run only after safe ownership release and while the engine permits new claims. One real committed human reply resumes the task without replaying effects; finite run reports incomplete while waiting.
- **I15:** Compose arbitrary intent using typed prose, long multiline pasted blocks and several images/files. Compact tokens can be inspected, edited or removed without accidental submission. Resize/back-navigation preserves the draft. Saved `specs/_initial.md` retains original text exactly and ordered relative attachment links, without summaries, placeholder labels or temporary-machine paths. It is versioned with the ordinary Expert task before dispatch. Customized task-source paths still resolve the link.
- **I16:** The dedicated Traces screen asks all three choices and saves their explicit values in `ptbk.json`. Defaults are local-only traces, ignored videos and enabled browser recording. Effective parent/video exclusion is visible; resume reuses answers. Noninteractive equivalents preserve false values and fail actionably for genuinely missing required decisions rather than prompt invisibly.
- **I17:** Initialization creates a missing editable `agents/.core/chatter.book` with `AGENT Chatter` and TEAM access to all other initialized core/specialist roles, without self-consultation. Reinitialization preserves an existing customized Chatter, its team and all older core Books. An upgrade adds only a missing required role; invalid or colliding definitions are diagnosed, not overwritten. See [Chatter acceptance](../agents/chatter.md#acceptance-outcomes).

## Agents, language and assignment

- **A01:** `@Adam` and `{{Adam}}` are identical; existing `{Adam}` is a readable compatibility alias. Case/diacritics/separators are normalized before lookup for agents, tasks and chats. One shared deterministic resolver orders built-ins, nonignored common folders (shallow first; root order agents/tasks/chats), remaining nonignored Books and eligible ignored Books such as node_modules. The first matching named Book wins; colliding definitions are shadowed and diagnosed, not merged or intrinsically fatal. FROM/TEAM/TASK AGENT and other typed commitments require the correct winning kind; hidden/dependency Books are referenceable without automatic ordinary task discovery or edit authority. See [reference acceptance](../book-language/references.md#acceptance-outcomes).
- **A02:** Default inheritance reaches Adam; custom ancestors are allowed when the chain terminates. FROM cycles fail. Void/Null/0 ends inheritance and is a TEAM no-op; User fails in FROM and creates a request in TEAM; Expert works in both.
- **A03:** Reciprocal TEAM relationships are valid, consultations are bounded and the project still has at most one executing task. Advisors receive their own instructions and cannot exceed the originating task/conversation authority. Conversation-only advice does not manufacture a task or bypass the queue for actual specialist execution.
- **A04:** Start discovers enabled harnesses' global installations, authentication and models. Missing all usable enabled harnesses invokes setup or gives an unattended diagnostic. An otherwise actionable unassigned task automatically creates one checked Manager prerequisite before target execution, with a visible relationship and direct authorized bootstrap. It neither needs manual assignment nor recursively assigns itself. Explicit requirements and paid-account restrictions remain intact; retries/restart do not duplicate assignment work.
- **A05:** Implicit/explicit OPEN produces one Teacher follow-up; limited OPEN is respected. CLOSED prevents learning, including pending learning work. Teacher is customizable but must be CLOSED, and non-agents are not rewritten as local Books.
- **A06:** Canonical Books begin with AGENT, TASK or CHAT plus their name content, using one grammar and parser. Standalone Books need no folder hint to determine kind; moving one cannot change its kind. Multiline commitment content and fenced control-looking examples survive edits. Every documented commitment and alias has its declared meaning; malformed controls never silently activate work. Task GOAL describes bounded work, not an agent's ongoing discovery goal.
- **A07:** Verify complete multiword uppercase keywords, numeric/reference content and the three-letter minimum: a standalone A/I/AI in prose does not begin a commitment. Unknown full keywords are not shortened to known prefixes. TASK AGENT and CHAT MESSAGE are not root declarations; a missing, empty, repeated or unsupported root declaration receives a diagnostic. Legacy plain-name/ENTITY sources are explicitly converted with preserved identity, never silently rewritten during discovery. See [syntax acceptance](../book-language/syntax.md#acceptance-outcomes).

## Tasks and persistence

- **T01:** Agent, Task and Chat identities are the normalized name contents of their opening AGENT/TASK/CHAT commitments, excluding keywords, never generated IDs or filenames. Type does not introduce a separate name namespace. A same-name duplicate may exist: deterministic first-wins lookup selects one Book without merging; Fixer diagnoses shadowing. Moving a file preserves identity, renaming its declared name requires explicit link/history reconciliation. Eligibility, relationships and task routing use the selected name. The source-filename-based trace directory is storage, not a second logical identity.
- **T02:** Each accepted task result/occurrence has one commit containing checked changes, TASK DONE, follow-ups, task-internal agent↔agent conversation and eligible traces/video. Subject is `PTBK: <task name>`, body includes assignment and `Task-Name: <name>`, not Task-ID. Creation/assignment/repair remain distinct scoped operations with name correlation.
- **T03:** Run is finite and uses one configuration; start operates indefinitely. At most one project task executes across interfaces and service commands. Future high-priority work does not block ready work or trigger goal enquiry.
- **T04:** On start or queue completion with no unfinished present or future tasks and no active cooldown, a `running` engine begins goal enquiry automatically as ordinary checked work. Useful generated tasks run without a new start or manual Run action. An enquiry may create future work or no work. Cooldowns survive restart; supporting agents, unavailable goals and empty results do not cause an unbounded generation loop. Legitimate waits have visible reasons, not invented progress. Pausing, pause and stopping prohibit new discovery/assignment/follow-up task claims as well as ordinary backlog claims.
- **T05:** Earliest-start boundaries, explicit offsets and ambiguous local times are respected. Recurrence preserves anchors, task identity and occurrence history, coalesces downtime, never overlaps and runs at most one occurrence per finite invocation.
- **T06:** Interrupt during work, checks, a conversation, completion, commit or push. Safe recovery resumes the correct phase without duplicate execution/messages/commits, preserving source revisions, normalized names and historical trace evidence. Unrelated staged edits, hooks, signing and external effects are respected.
- **T07:** Commit/push failure never reruns successful model work. Full/partial reverts and changed dependencies are reconciled, including recorded external effects. Worktree integration preserves the single task commit and its identity or keeps an unintegrated result safely.
- **T08:** Legacy Markdown states, priorities, sections and selectors remain supported. Old ptbk-task-id comments are non-authoritative historical metadata and are never generated. Conversion preserves named work, assets, meaning, timestamps and provenance without creating two runnable copies.
- **T09:** Default add commits one unfinished `TASK <name>` Book before dispatch, with a creation-time-decorated name and its bounded description under GOAL, enabling Manager and start without manual Git. Other authorized versioned project changes commit by default. Each accepted human-facing message has a separate chat commit; task-internal TEAM messages join the task result. Read-only/no-op changes create no commits; unrelated edits and Git ownership remain protected.
- **T10:** Explicit `--no-commit` on init, add, run or start creates no automatic commits and visibly reports uncommitted state, preserving names, local traces, checks, ownership and recovery without rerunning accepted work. The opt-out propagates through init's automatic service start but does not silently change another process or later invocation. It conflicts with isolation and auto-pull/push; its own writes do not require ignoring unrelated changes. Reentering default mode requires safe reconciliation, not a surprise aggregate commit.
- **T11:** All new task/chat generators include readable date/time before any collision: add, chat entry points, approved plans, bootstrap, automatic assignment/discovery/learning/repair, follow-ups and consultations. Repeated descriptions, a fixed clock, batches and concurrent writers still produce distinct final normalized names without overwriting paths or shadowing another entity kind. Links and outcomes use the saved names, not title-only guesses. See [generated-name acceptance](generated-names.md#acceptance-outcomes).
- **T12:** Valid names with no date or a differently formatted date remain valid ordinary text. The parser never extracts or requires a timestamp from a name. Existing-source conversion, pending-save retry, recovery and recurring execution retain the name and its trace/history association. Filenames remain separate date-leading storage names; a file move does not change kind or logical identity.

## Controls, access and evidence

- **U01:** Attached/foreground terminal views, browser SPA and direct API clients show and control one engine and its actual version. Lifecycle controls, wait skipping, settings and answers synchronize; startup-only settings and deferred changes are explicit. Multiple attached clients do not create queues or own service state. Closing an attached terminal/browser client never stops the engine; an explicit shared stop operation does.
- **U02:** TEAM User, system confirmations and browser logins all create agent-authored chats (not a separate persistent Request entity). A waiting question is conversational and attributed; terminal/browser/API/CLI can answer once. `ptbk answer` is a compatibility chat reply, even without HTTP; raw output never prompts invisibly.
- **U03:** New projects default to a dedicated OS-user-global Promptbook-managed Chrome-compatible profile reused across projects without touching personal Chrome. Alternative choices remain isolated project profile, user's existing Chrome profile and custom profile path; headless/headful is independent. Concurrent owners cannot corrupt a shared profile and existing selections survive reinit.
- **U04:** Harness native authentication and browser website sessions remain independent: changing a browser profile does not log out/reinitialize a harness. No password database, key or session data appears in Git, traces or ordinary API state. Protect browser video against sensitive authentication material too. External content cannot become authority to change rules; localhost or a public tunnel hostname does not bypass authorization.
- **U05:** Read-only services work offline without mutation, initialization, updates, tunnel startup or paid calls. Plan cannot implement or delegate writes; fix does not run backlog work; verify remains human review.
- **U06:** Logs, usage and status describe observed outcomes, with unknown data and truncation explicit. Teacher uses only exposed evidence. Low disk, unavailable login, quota and repeated failures preserve work and keep a running daemon controllable. Optional evidence-capture failure does not unnecessarily stop safe work.
- **U07:** Init remains finite with Step X of Y, Expert guide and brief celebration only after confirmed setup/start; it neither opens dashboard nor waits for bootstrap. Dashboard is an indefinite operational view. `ptbk chat` is a separate persistent conversation experience, while `add` is finite model-free task authoring. Rich input, resize and navigation preserve drafts.
- **U08:** Bare/help/about, wizard headers and runtime dashboards show the invoked/running engine version, including when another installed version or a newer release exists. Help remains structured and readable in a narrow terminal or redirected output, without harness configuration dumps or setup side effects.
- **U09:** Failures before, during and after task execution explain the failed phase, effect and next action, with actual redacted diagnostic evidence and versions. Trace-storage failure is explicit, with available stderr diagnostics, not a fictitious saved path. Commit/push failures do not repeat successful model work.
- **U10:** All predefined choices are keyboard-selectable, including four browser profiles, harnesses, traces and chat answers, with Enter for focused default and Esc for cancellation. New chat first offers Chatter (focused default) or Choose another agent. Only the second opens the full valid target list including hidden/core and Expert; User/Void/Null are not speakers. Freeform chat uses the rich composer.
- **U11:** Suitable terminal/browser views use distinct labeled attention, work, visible service-controls, queue, activity/results and connection panels rather than one large rectangle. Execution and browser technical details are initially collapsed, with discoverable shortcuts; lifecycle actions are not hidden in them. Agent mascots retain stable identity/truthful activity. Narrow/reduced-motion views preserve names, state, controls and request priority. Lifecycle commands render one grouped outcome/snapshot; raw output has no decoration, QR art, hidden prompts or automatic pairing-secret disclosure. See [layout](dashboard-layout.md) and [visual acceptance](../agents/visual-identity.md#acceptance-outcomes).
- **U12:** Dashboard attaches to an existing engine with no second worker. Q/Ctrl+C leaves only client; C starts a new Chatter-first chat, A opens the highest-priority existing waiting conversation, and all-chats exposes the other threads. Direct chat also uses the shared picker; Ctrl+C there closes chat only. Disconnection never drops stored messages or releases the engine lock.
- **U13:** The lightweight SPA consumes authenticated service API, including lists/history/authoring/answers for chats and task links, without server-rendered runtime HTML. Messages commit exactly once, reflect across terminal/browser/API and reject stale duplicate responses. Refresh/tunnel failure cannot create tasks, duplicate chats or stop the daemon.
- **U14:** Bare `ptbk`, `ptbk help` and `ptbk --help` show the top-level overview. `ptbk init --help`, `ptbk init help` and `ptbk help init` show only init; start/dashboard/add and aliases follow the same rule, as do supported nested subcommands. Pretty and raw retain the same relevant options/defaults/examples without unrelated command dumps. Scoped help works offline without setup, required command inputs or a running service and never executes the command; invalid paths and usage errors identify the relevant scope instead of silently falling back to global help. Pause/resume, stop --force/-F and dashboard --global are documented in their appropriate command scopes.
- **U15:** Default startup on a connected supported system supplies protected remote access: scan the local pairing QR on a phone using mobile data, authenticate, inspect state and answer a request visible locally. Bare public URLs reveal no project content or authority. Pairing is short-lived/single-use, explicitly renewable locally and devices are revocable. Read-only status/refresh does not mint or rotate capabilities; credentials stay out of ordinary API output, redirected output, logs and Git. Cross-origin and stale/reused pairing attempts fail safely.
- **U16:** No-tunnel makes no provider connection while preserving local HTTP; no-server disables both and conflicts with explicit tunnel enablement. No-QR/raw changes no exposure policy. Repeated start and additional clients create no extra tunnel. Provider/network failure is visibly degraded without indefinitely stopping local safe work or falling back to unprotected exposure. Stop/restart/finite-run completion manage the owned tunnel, and changed ephemeral addresses invalidate stale connection claims. See [remote-access acceptance](remote-access.md#acceptance-outcomes).
- **U17:** Expand execution details and read the actual agent, harness, concrete model and thinking level together, including overrides and distinct attempt/consultation contexts. Automatic/unreported/unsupported metadata is distinguished without guessed equivalents. Switching tasks clears stale current-run claims. Raw/API and browser retain the same information; closing the panel does not mutate engine state.
- **U18:** Expand browser details for each profile source and inspect the effective resolved path, browser/mode, ownership and launch/connection health. Inject launch failure and verify real redacted diagnostics and bounded automatic repair with no viewer open. Manual recheck, startup retry and browser restart use the same engine recovery, with deferred safe-boundary outcomes visible. They preserve sessions, active-work evidence and unrelated browsers, and do not restart the engine. Significant blockers remain visible when details are collapsed.

## Service lifecycle and exclusive ownership

- **L01:** Observe exactly running, pausing, pause and stopping as live engine states through CLI, two terminal dashboards, browser and API. Running can be idle; task phases and blockers are separate. An exited service is an observed absence, not a live stopped state. Force stop is an immediate action and no hard-pause operation exists.
- **L02:** Request pause during an active task: no next task is claimed, current work settles once, then the engine remains alive in pause. Request graceful stop during active work: the same drain ends in owned cleanup and exit. Cover checks, pending result persistence and safely checkpointable human waiting. No implicit force escalation or routine human response is needed merely to finish a safely checkpointed shutdown. Pause with no active task is immediate.
- **L03:** Cancel pausing or stopping via resume and observe running without replaying the current task. Switch pausing to stopping and stopping to pausing without task interruption; stop-to-pause explicitly confirms cancellation of shutdown. Noninteractive conflict handling never waits on a hidden prompt. Repeated requests are idempotent, stale confirmations cannot overwrite newer intent, and cancellation after irreversible shutdown is reported too late rather than falsely successful.
- **L04:** From pause, resume normal work, stop immediately and orderly, or restart into one running replacement. Force stop from pause also uses the quick orderly shutdown because no task needs interruption. Main dashboard controls and commands invoke identical operations, including cancellation and pending-intent changes; another viewer immediately reflects the resulting state.
- **L05:** `ptbk stop --force` and `ptbk stop -F` immediately stop only the selected owned execution without claiming completion of unfinished work. The owning service makes a bounded cleanup attempt, including its own lock; controlled graceful shutdown also cleans up. An external uncatchable kill has no cleanup guarantee or new next-start lock-deletion requirement. A signal to an attached dashboard closes only that viewer. Never terminate unrelated processes or remove a replacement owner's lock.
- **L06:** Restart drains through stopping with visible restart intent, releases the old owner and starts exactly one replacement using the same project, effective configuration and selected installation. It never overlaps workers or silently changes foreground placement into a daemon. Cancelling pending restart cancels its replacement start. Lost replies, startup failure and unconfirmed stop outcomes are truthful; no blind mutation replay targets a successor. A completed intentional stop suppresses persistence, but cancelling pending stop leaves no accidental permanent-stop setting.
- **L07:** Start one project concurrently through global/local installations, different supported versions and equivalent paths. Exactly one engine owns its project lock. Attach three dashboards from the same project, change state in one and observe it in all, then close all viewers: the engine continues. Paused ownership still excludes another engine. Dashboard attachment, global registration and navigation never acquire or release the project lock. Preserve recovery data, sessions and evidence during owned cleanup.

Do not bypass OS permissions or reveal credentials. Dead discovery records are not permission to delete project locks. Stable selection must not jump to another live row when its previous target exits. See [global-dashboard acceptance](global-dashboard.md#acceptance-outcomes).

## Unattended operation and audit trails

- **O01:** On an awake supported host with available dependencies and a selected authenticated browser, configure an authorized recurring AI-news publishing agenda and simulate a month with no dashboard client or operator. Scheduled work and follow-ups continue without routine per-post approval; the user can inspect results and retained task-linked evidence on return. Respect explicit pauses, schedules and scope; do not invent activity when legitimately idle.
- **O02:** Inject temporary network/provider failures, a restart and an unexpected harness input wait. Detect and classify the conditions, recover within budgets and resume the correct phase without duplicated publication or unlimited paid polling. An alive but avoidably stalled service fails this scenario. Required login, genuinely missing authority or irreconcilable ownership creates one clear exceptional request; safe independent work can continue when lifecycle state permits it.
- **E01:** Each canonical task has a `traces/<task-file-basename>/` root audit directory matching the actual source filename literally without its final `.book` extension, not its normalized TASK name or a generated ID. Verify with deliberately different source filename and declared name, preserving date/case/other supported filename characters and custom task-source locations. Consolidated available harness text and events retain attempts, occurrences, declared names, source revisions, linked chats and Git evidence without invented private reasoning.
- **E02:** Browser work in headless/headful can be followed from the named task through Git history to exposed harness text and playable attributed video. Record actual transitions/gaps, exclude secret/authentication entry and unrelated desktop activity; unsupported/failed capture is honestly disclosed.
- **E03:** Exercise all combinations of trace commit, video ignore and recording settings. Whole-tree exclusion takes precedence; recording remains independent. Selected traces and finalized eligible video share the result commit with completion and accepted changes. Excluded artifacts remain local and are not force-added. `.ptbk/` remains ignored. Changing policy preserves historical/local evidence and unrelated ignore rules.
- **E04:** Interrupt capture and result persistence, then recover. Evidence remains linked to the same task and distinct attempts. No self-referential commit-SHA bookkeeping loop appears; post-commit events are retained honestly. Retention/truncation is visible and preserves pending-work evidence; missing storage produces truthful diagnostics rather than fictional paths or a repeated external action.
