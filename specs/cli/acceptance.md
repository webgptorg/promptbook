# Acceptance scenarios

[Main specification](../_main.md)

These are verifiable product outcomes, not an implementation plan or evidence of completed tests. Exercise common behavior with local fixture projects and deterministic substitutes; paid provider checks are separate and explicit. Topic specifications add focused acceptance outcomes. Unless explicitly testing an exception, use automatic commits; [uncommitted workflows](git-persistence.md#explicit-uncommitted-workflows) are tested separately. Configuration/tool identifiers follow their [naming contract](../coding-standards/naming.md), independently of free-form Book names.

## Installation and startup

- **S01:** Global `ptbk` and project-local `npx ptbk` work outside this repository. Two projects use different versions, and their daemons and Experts use the correct installation after restart.
- **S02:** Successful init saves technical setup, the original initial specification and one ordinary Expert task, then automatically starts the background agenda. It does not execute Expert inside the initializer, create an Expert project file or add a duplicate generic starter. Repeating satisfied initialization preserves source, creates no empty commit or duplicate task, and reuses an existing service without resetting it.
- **S03:** Plain start creates one daemon with persistence and a free loopback HTTP port, reports launch and automatically attaches the independent project dashboard in ordinary interactive use; `--no-dashboard`, raw/no-UI/noninteractive or redirected use returns without a viewer. HTTP remains loopback-only without provider contact or software installation. No-server and an explicit port behave as advertised; a port conflict is not reported as success. Bare interactive `ptbk` offers exactly two choices: focused init/start/dashboard according to the selected directory's actual initialization/engine state, followed by Help. Selection uses the existing workflow; cancellation has no effects. Noninteractive bare invocation shows technical help.
- **S04:** Start/pause/resume/stop/restart/status/show target the correct project and distinguish an accepted pending request from completion. Interactive daemon start/restart attach the dashboard by default, including start over an existing owner; suppression modes and other lifecycle commands report once. Repeated/concurrent starts do not duplicate the engine, cancel deliberate pause/stop intent or control an unrelated PID. Status/show never start work; an intentional completed stop remains stopped after reboot until an authorized start, including a subsequent explicit init's start operation.
- **S05:** Verify daemon reboot/crash recovery on Linux, macOS and Windows: running restores under current readiness/Health; manual pause, including pending drain, is restored before any background claim. Health-only reasons are re-evaluated and may clear; combined pause retains manual intent. Deliberate stop/force stop/panic stays stopped through supervisor retries/reboot until explicit start. No-persist disables automatic restart but retains data and known-project registration. Raw daemon/foreground placement and missing persistence prerequisites remain truthful.
- **S06:** Successful init begins eligible work automatically without a separate start, setup prompt, manual assignment, open dashboard or additional work-launch action. A later plain start reuses that service. After intentional stop, explicit start resumes processing. Assigned work executes, unassigned work runs Router then its target, and due discovery produces useful tasks when prerequisites exist. Later missing tools keep the engine running with a resource wait rather than requiring a restart or another setup wizard.
- **S07:** The official **Check ptbk** workflow passes on Node 22/24 across Linux, macOS and Windows for the accepted source. An authorized **Publish ptbk** release validates its exact tag through that matrix, publishes and verifies the package, and finishes successfully. Both workflows must pass for release acceptance; a failed required platform job or skipped publication is unsuccessful. Failed validation blocks publication and remains visible; code/test fixes use a new immutable release tag. See [GitHub Actions checks and publication](releasing.md).

## Initialization, configuration and maintenance

- **I01:** With dependencies available and no update selected, intent is the first input. Blank intent, an empty destination and usable selected browser/harness tools produce a useful skeleton, preserved blank `specs/_initial.md` and one ordinary Expert readiness task. No check-command question appears; absent real validation receives the explicitly labelled informational placeholder, which does not block start or claim tests passed. Setup prefers global CLI use, installs the exact running version locally only when selected, saves its `promptbookVersion` and commits without model work; the daemon executes bootstrap normally. Repeating satisfied setup is a file no-op, including after task completion/archiving.
- **I02:** Existing files, Git history/current branch, staging, customized agents/settings and a declared devDependency survive init. Reinitialization reuses recorded intent without reauthoring the project's purpose. Partial setup/new required roles receive only missing support; required configuration evolution uses its separate migration pass. Unrelated changes never enter setup commits, and original specifications/assets and real checks are not overwritten. A newly created repository uses main; an existing branch is preserved.
- **I03:** Start over genuinely missing structural setup offers the same initializer for the selected folder and rechecks readiness. Initialized projects bypass it, including those waiting for deliberately disabled/missing tools. One handoff creates one service without recursive init/start. Raw/noninteractive use never launches hidden setup/login prompts and identifies genuinely missing decisions/prerequisites.
- **I04:** Creating a child inside Git offers back, an ignored independent repository or a real submodule. Back changes neither project; ignored-child and submodule metadata are correct and repeatable. Child commits and parent changes stay separate; no invented remote, accidental parent commit or unrelated index changes occur.
- **I05:** Global and parent-local invocations creating a new destination offer Use the global CLI first/preferred and destination-local dependencies second. Selecting local installs the exact running version, not latest. Existing local dependencies/devDependencies are preserved; selecting global does not silently add a local copy or claim a parent-local executable is global.
- **I06:** An outdated invoked engine offers an early optional self-update after intent, defaulting to yes. No keeps the current version only when compatible with the saved project version. Yes updates the correct installation and exits before setup with a rerun instruction and recoverable intent/assets. Offline lookup and failure are honest; unattended use never silently accepts an update. A known newer project configuration still requires the compatibility gate, and rerun does not require repasting the draft.
- **I07:** Plugin/engine defaults, project settings and explicit overrides resolve in documented order, preserving false/empty values and path bases. Temporary flags/controls do not rewrite defaults; explicit saved tool management does commit its own changes. Secrets and runtime state never enter JSON. Trace and init-to-service settings use the same precedence, canonical naming and live-refresh rules.
- **I08:** A catalog of hundreds initially shows only featured names and More, with all integrations reachable. Selecting one configures only that integration; an authenticated global installation is reused. Supported/installed but unconfigured or disabled tools are not implicit routing/update candidates. Init, runtime, CLI and dashboard use the same typed tool/plugin contracts, not separate implementations.
- **I09:** One outdated selected harness offers yes/no; several offer keep, update all outdated selected, or choose individually. Current/unselected harnesses are untouched. Start automatically maintains enabled harnesses by default, honors disabling overrides and avoids updating an active shared invocation. Several account instances sharing an executable do not cause duplicate competing updates. Failure preserves a usable compatible version or visibly blocks only affected work.
- **I10:** Select two initial harness integrations, one healthy and one needing login/setup. Init verifies both selected integrations and the initial browser, unless the user explicitly removes a selection; an opened login window is not completion. The placeholder check is accepted without a check setup question or validation-deferral blocker. Cancelled essential login, unresolved dependencies or failed local setup commit is incomplete. Failed remote publication does not block otherwise ready local launch. Failed service launch preserves saved setup and queued work; resume reuses completed steps.
- **I11:** The first task is assigned to Expert and links to the original specification from its actual task-source location. It adapts project content, agents, checks and follow-ups without replacing original input. Ordinary execution/traces/completion/result commits apply. A placeholder is not real verification evidence; genuinely configured failing checks cannot be stamped passed or replaced with a fake success. Init does not run project checks or claim they passed; existing validation and tasks remain intact.
- **I12:** A native globally installed Codex reporting `Logged in using ChatGPT` is ready without another login, API key, `--allow-credits` or model probe, even without credit-control flags. Native execution/TEAM/planning retain that context and ambient keys do not override it. An explicitly configured API_KEY tool is a distinct authorized route/fallback with a symbolic key reference. Quota/credit failures remain real outcomes; no unconfigured paid fallback, fabricated provider control or shared-login overwrite is permitted.
- **I13:** Launch a project with a healthy globally installed Codex on a custom/version-manager PATH and native login store. Resume its saved worker under an OS-manager environment lacking those locations: it still detects that same account without a login or model probe. Missing-harness and recovery blockers remain labeled throughout recheck delays, even after their action request is answered. Actual cause, next action and recheck are visible in terminal/browser/API; Skip wait cannot bypass them. Older saved workers retain the pinned Node global bin fallback.
- **I14:** A genuine User clarification reuses its source/designated chat with the asking agent declared before speaking, or creates/links one when none exists, ends the provider turn promptly and checkpoints without retries or another model call. Restart preserves the exact chat/question and task context. Independent work runs only after safe ownership release and when lifecycle permits new claims. One real saved applicable reply immediately clears its question's attention and resumes without replaying effects.
- **I15:** Compose arbitrary intent with prose, long pasted blocks and several images/files. Compact tokens can be inspected/edited/removed without accidental submission; resize/back navigation preserves the draft. `specs/_initial.md` retains original text exactly and ordered relative attachment links, without summaries, placeholders or temporary-machine paths. Save it with the ordinary Expert task before dispatch, including customized source paths.
- **I16:** The Traces screen saves explicit `traces.isCommitted`, `traces.isVideoIgnored` and `traces.isVideoRecordingEnabled`. Defaults are local-only traces, ignored videos and enabled recording. Effective parent/video exclusion is visible; resume reuses answers. Noninteractive equivalents preserve false and never prompt invisibly for missing decisions.
- **I17:** Init creates a missing editable `agents/.core/chatter.book` with `AGENT Chatter` and TEAM access to all other initialized core/specialist roles, without self-consultation. Reinit preserves customized Chatter/team and older core Books. Init/start add missing required roles through shared preparation and reconcile old/new templates against local edits. Clear changes apply automatically, conflicts go to Fixer before necessary human decisions; invalid/colliding definitions use repair rather than replacement. See [Chatter acceptance](../agents/core-agents/chatter.md#acceptance-outcomes).

## Agents, language and assignment

- **A01:** `@Adam` and `{Adam}` are identical; multiword names use single braces (`{Frontend Developer}`) and `{{Adam}}` is not a reference. Case/diacritics/separators are normalized for agents/tasks/chats. One shared resolver orders built-ins (Void/Null, Expert, User), then every Book in `agents/`, then the rest of the nonignored project (tasks/, chats/, other locations), then eligible ignored Books such as node_modules. First matching named Book wins; collisions are shadowed/diagnosed, not merged or intrinsically fatal. Typed references require the winning kind; hidden/dependency Books are referenceable without automatic discovery/edit authority. See [reference acceptance](../book-language/references.md#acceptance-outcomes).
- **A02:** Default inheritance reaches Adam; custom ancestors are allowed when the chain terminates. FROM cycles fail. Void/Null/0 ends inheritance and is a TEAM no-op; User fails in FROM and creates a request in TEAM; Expert works in both.
- **A03:** Reciprocal TEAM relationships are valid, consultations are bounded and at most one project task executes. Advisors receive their own instructions and cannot exceed task/conversation authority. Conversation-only advice neither invents a task nor bypasses the queue for actual specialist execution.
- **A04:** Before every task and during waits, discover current enabled tools, global harness executables, authentication/models and browser readiness. Missing resources in an initialized project produce a running resource wait, not automatic reinitialization or service exit. Otherwise actionable unassigned work creates one checked Router prerequisite with a direct authorized bootstrap and visible relation, without recursive assignment. Explicit requirements/paid restrictions and retry deduplication remain intact.
- **A05:** Implicit/explicit OPEN produces one Teacher follow-up; limited OPEN is respected. CLOSED prevents learning, including pending learning work. Teacher is customizable but must be CLOSED, and non-agents are not rewritten as local Books.
- **A06:** Canonical Books begin with AGENT, TASK or CHAT and their name content, using one grammar/parser. Standalone Books need no folder hint and moving one does not change kind. Multiline content/fenced control-looking examples survive. Documented commitments/aliases retain meaning; malformed controls do not activate work. Task GOAL is bounded assignment, not an agent's ongoing discovery goal.
- **A07:** Verify full multiword uppercase keywords, numeric/reference content and the three-letter minimum: standalone A/I/AI in prose is not a commitment. Unknown full keywords are not shortened into known prefixes. TASK AGENT/CHAT MESSAGE are not roots; missing/empty/repeated/unsupported roots are diagnosed. Legacy plain-name/ENTITY sources are explicitly converted preserving identity, not silently rewritten during discovery. See [syntax acceptance](../book-language/syntax.md#acceptance-outcomes).

## Tasks and persistence

- **T01:** Agent/Task/Chat identity is normalized opening-name content, not generated ID or filename; kind does not create separate name namespaces. First-wins duplicate lookup selects one without merging; Fixer diagnoses shadowing. Moving preserves identity; declared rename requires link/history reconciliation. Routing/relationships use the selected name, while source-filename trace storage remains separate.
- **T02:** Each accepted task/occurrence has one result commit containing accepted/check-generated changes, TASK DONE, follow-ups, task-internal conversation and eligible traces/video. Subject uses lowercase `ptbk: `, the executing agent's backtick-quoted textual visual and a meaningful task subject, with assignment and `Task-Name`, not Task-ID. Creation, assignment, repair and later integration remain separately scoped operations with provenance.
- **T03:** Start is the ongoing work launcher; no `ptbk run` remains. Live tools refresh throughout execution. Tasks and chat work share `execution.maxConcurrentWork`, default five, across interfaces; one working tree/current branch and per-file ownership permit different-file concurrency and block same-file conflicts. Chat and its routing remain eligible during pause; future high-priority work does not block ready work or trigger premature goal enquiry.
- **T04:** With no unfinished present/future work and no active cooldown, a running engine with usable resources performs ordinary goal enquiry automatically. Useful tasks execute without another command; enquiry can create future work or no work. Cooldowns survive restart; unavailable goals/supporting agents/empty results do not busy-loop. Pausing/pause/stopping prohibit new background discovery, task-assignment and follow-up claims as well as ordinary background claims. Chat and its required routing remain available in pausing/pause without consuming a second task owner.
- **T05:** Earliest-start boundaries, explicit offsets and ambiguous local times are respected. Recurrence preserves anchors, identity/history, coalesces downtime, never overlaps and executes at most once per finite invocation.
- **T06:** Interrupt during work, checks, conversation, completion, commit or push. Resume the correct safe phase without duplicate execution/messages/commits, preserving revisions, names, traces, staging, hooks/signing and external effects.
- **T07:** Commit/push failure does not rerun successful model work. Reconcile reverts/changed dependencies with effect evidence. Worktree integration preserves the original result commit and intervening project commits using a visible non-fast-forward merge, or keeps unintegrated work recoverable. No rebase/amend/force reset replaces history to make integration succeed.
- **T08:** Legacy Markdown states/priorities/sections/selectors remain supported. Old ptbk-task-id comments are historical non-authoritative metadata and not generated. Conversion preserves named work, assets, meaning, timestamps and provenance without two runnable copies.
- **T09:** Add normally commits one unfinished typed/date-decorated task with bounded GOAL before dispatch, enabling Router/start without manual Git. Other authorized versioned changes commit by operation. Messages/files save immediately; compatible conversational saves use bounded debounced commits and task-internal TEAM retains result attribution. Read/no-op creates no commit; unrelated edits remain protected.
- **T10:** Ordinary `--no-commit` init/add/start visibly preserves uncommitted work without invented SHAs or rerunning accepted effects, and propagates through init's service only. It conflicts with autosync; task-worktree isolation is removed, and cannot silently disable mandatory configuration-migration or explicit tool-management commits: incompatible requests fail before those writes. Owned writes do not require ignoring unrelated dirt. Reentering default mode reconciles safely rather than creating a surprise aggregate commit.
- **T11:** New task/chat generators include readable date/time before collision: add/chat/plans/bootstrap/assignment/discovery/learning/repair/follow-ups/consultations. Repeated text, fixed clocks, batches and concurrent writers still produce distinct normalized names and paths without shadowing another kind. Links use final names. See [generated-name acceptance](generated-names.md#acceptance-outcomes).
- **T12:** Undated/differently dated existing names remain ordinary valid text. Parser never requires/extracts a name timestamp. Conversion, pending-save retry, recovery and recurrence retain existing name/history. Filenames are separate date-leading storage; moves do not change logical identity/kind.

## Service lifecycle and exclusive ownership

- **L01:** CLI, terminals, browser and API observe exactly running, pausing, pause, stopping as live states. Running can wait for tools/tasks/sync; blockers/phases are separate. Exited is observed absence, not fifth live state. Force stop is immediate; no hard-pause operation exists.
- **L02:** Pause prevents next claim, lets current work settle once and remains alive. Graceful stop uses the same drain then cleanup/exit, covering checks, pending commit and safe human-wait checkpoints. No implicit force or routine human reply is required merely to checkpoint shutdown. Pause without current work is immediate.
- **L03:** Resume cancels pending pause/stop without replay. Changing pausing to stopping or stopping to pausing preserves current work; cancelling shutdown for pause is confirmed. Noninteractive choices are explicit, repeated requests idempotent, stale confirmations cannot overwrite newer intent, and cancellation after irreversible shutdown reports too late.
- **L04:** From pause, resume work, stop orderly or restart into one replacement. Force stop while idle still attempts bounded owned cleanup. All clients invoke the same operations, including cancellation/intent changes, and immediately see the same state.
- **L05:** `ptbk stop --force`/`-F` immediately terminates the selected engine and every owned harness/helper/browser execution process, including unresponsive owners, without waiting for work to finish or deleting tools. No owned worker continues after parent exit. Cleanup is bounded/best-effort; uncatchable kill has no cleanup guarantee/new lock-removal requirement. Viewer signals close only viewer. Never kill unrelated processes or remove a successor's lock.
- **L06:** Restart drains visibly, releases old owner and launches one replacement with the same project/effective installation and placement, without overlap. Cancelling pending restart cancels replacement start. Lost replies/start failure/unconfirmed stop are truthful; no blind replay targets a successor. Completed deliberate stop suppresses persistence, while cancelled stop does not leave permanent stop intent.
- **L07:** Concurrent starts across global/local versions and equivalent paths produce one project owner. Several dashboards share state, but none acquires/releases the lock; closing all leaves engine active. Pause still excludes another owner. Preserve recovery/session/evidence during controlled cleanup.
