# Project initialization

[Main specification](../_main.md) · [Initialization experience](initialization-ui.md)

`ptbk init` (`ptbk initialize`) is a finite technical setup workflow for an empty or existing folder. It prepares support, preserves original intent, saves one ordinary Expert bootstrap and starts the agenda in the background. Project-specific content is created by that task, not a second execution mechanism inside init. Presentation/progress/celebration belong to [initialization UX](initialization-ui.md).

Reuse the same readiness/setup operations from start for genuinely missing initialization, with one handoff and no recursive init/start or duplicate workers. Equivalent decisions can be supplied noninteractively. Later missing/disabled tools in an initialized project are a live resource wait, not permission to rerun the wizard or repopulate deliberately removed resources.

## Initial input and destination

For new initialization, first ask what the user is working on, before destination/installation questions. Accept arbitrary intent, not just software: free text, long pasted material, images and files. Reuse supplied input, resumed drafts or an existing initialization's recorded intent. Reinit/upgrades preserve purpose rather than requesting a new brief.

Offer destinations in this order: **New project in the shared Promptbook projects folder** (preferred), **Current directory**, **New subfolder of the current directory**. Explain both workflows: add Promptbook to existing work, or start a new agenda without having to choose its filesystem location first. The shared default is `<resolved-user-home>/PTBK/project/<project-folder>/`, one child per project, under the [cross-platform home/sudo policy](workspace.md#home-directory-and-shared-projects-root). Show an editable folder name and resolved destination, validate collisions/writability, reuse an explicit destination and confirm location before writes. Never initialize the shared container itself as the project. Nonempty content is an existing project, not permission to regenerate it. Children inside Git follow [nested-project initialization](nested-projects.md). The optional [engine-update gate](updates.md) must not displace or lose the original intent/draft; an existing newer-version configuration also follows the [compatibility gate](configuration-migrations.md).

The [Windows installer](windows-installer.md) or [VPS launcher](vps-onboarding.md) may launch this same interactive workflow in a newly created empty directory, explicitly selected with `--path`. Reuse that destination rather than offer another root/subfolder decision; after the normal intent input, show it for confirmation. Installer folder naming is not the project's intent. Do not add an installer-specific initialization path: dependency choice, Git setup, tools/authentication, version checks, setup commit and automatic start retain their ordinary semantics. A VPS launcher without a supplied destination retains the ordinary home-based destination choices under the actual engine user's home, not its privileged installer's working directory.

Save accepted input in the initialized project's `specs/_initial.md`, preserving text verbatim: language, wording, whitespace, line breaks and long pasted blocks. Do not summarize, translate or improve it. Save original attachments as project-local assets with ordered working relative links at their corresponding positions. Composer tokens are presentation, not saved replacements for full content. Never retain clipboard/temp-file/absolute-machine references.

These are the initialized project's specifications, not changes to the engine's own specification folder. Prepare them with the [first task](first-task.md). Resume/reinit never overwrites original intent or duplicates attachments. Blank input remains blank; retain the useful default noncore agents and boilerplate so this is a starter project, not a technically empty one. Its ordinary Expert task performs a bounded readiness review without inventing purpose. With nonblank intent, create/adapt specialists relevant to the actual agenda instead of keeping irrelevant sample roles in every new project; reinit preserves existing user-owned roles.

## Incremental technical setup

Check Git, configuration, source locations, instructions, core agents, templates and ignore rules individually; resume only missing setup. Reuse a valid existing repository/current branch, including an unborn one. When creating a new repository, explicitly initialize **main**. Preserve files, staging, history and customization.

Prepare `agents/`, the configured task source (normally `tasks/`), `chats/`, `specs/`, root-level `traces/`, readable instructions, required [core agents](../agents/core-agents.md) and useful role/task templates. For blank initial intent, ordinary noncore defaults include Developer, Planner, Lawyer and Copywriter with useful TEAM relationships. For supplied intent, the ordinary bootstrap establishes relevant specialists. Ensure all required cores, including Tasker, through the same [preparation/update operation](../agents/core-agents.md#shared-preparation-and-template-updates) used by start. Initialize Router with a fully determined MODEL from the first suitable enabled selected harness and its coded plugin defaults, without another question. Preserve existing customized core content through the common three-way template update policy; an unusable existing Router follows common diagnostics/repair instead of recursive routing. Initialize Fixer with the simple general problem-solving Book and User/Expert TEAM under [automatic repair](../concepts/automatic-repair.md), never reset its customized/learned policy.

Create a missing `agents/.core/chatter.book` with `AGENT Chatter` and TEAM access to all other initialized/selected core/specialist roles plus Expert, excluding itself. Build its initial team from the completed role set, not just earlier-created files. Reinit preserves existing user-owned Chatter/team changes and other Books under the common core update policy. This is technical setup, not an extra chat, model call or bootstrap execution.

Apply the destination-specific [installation choice](installation.md), with **Use the global CLI** first/preferred and local installation second, preserving existing dependencies. For a fresh selection, preselect every detected installed **and ready** harness variant, without paid inference probes. Executable presence alone is insufficient; verify login/configuration. Preserve previous/explicit selections and deselections. Configure selected harness variants through the existing featured/More flow, with global installations, native login and [update choices](harness-updates.md). Complete and verify all initially selected integrations without paid readiness probes; cancellation/deferred selection remains incomplete unless explicitly removed. Reuse valid Codex ChatGPT authentication without requiring an API key or absent credit-control flag; see [harness account rules](harnesses.md).

Configure one browser through the existing four-source picker, defaulting to the dedicated reusable global Promptbook profile, not personal Chrome. Save typed named records in `tools` by calling the **same domain operations** as later CLI/dashboard management. Generate simple names and defaults. Do not ask users to build multiple-account pools, several browser instances or fallback chains during normal init. These remain available afterwards. Resolve known execution permissions during attended setup rather than leave invisible prompts in the daemon.

On a VPS without a usable display, default this browser to headless while retaining the same profile picker and explicit choices. An ordinary SSH terminal is sufficient for the technical initializer; authenticate selected harnesses through shared [remote-compatible native login](harness-authentication.md), without requiring a browser or desktop on the server. Recheck readiness under the same user/environment as the service before completing that setup step. Website-session workflows remain separate from the project browser's headless setting and harness login. Follow [VPS onboarding](vps-onboarding.md) for terminal and service-account handoff.

Write the actual running engine version into a new `promptbookVersion`. Existing older configurations use the ordinary migration pass, with its separate committed provenance, not an ad hoc initializer conversion. Preserve `.ptbk/`, browser/session stores and `.env` as ignored; [environment edits](environment.md) are non-destructive and timestamped.

Collect/reuse the three Traces choices: `traces.isCommitted`, `traces.isVideoIgnored` and `traces.isVideoRecordingEnabled`. Their defaults, dependencies and effective ignore rules live in [trace configuration](trace-configuration.md). Trace directories use literal task source basenames, independently of logical names.

## Optional Wallet setup

Offer **Set up Wallet now?**, default **No**. No leaves Wallet/encryption available for later setup from its dashboard or first protected use. Yes calls the exact same shared Wallet/encryption initialization operation, including protected presentation of the 12 recovery words. Do not duplicate logic in the wizard or recreate an existing vault. Noninteractive use supplies the equivalent decision without hidden prompts. After chosen/reused setup, offer the shared optional [Bitwarden import](wallet-import.md) with individual/all/none selection. Wallet No skips import; no import is valid. Preserve existing items and shared duplicate/conflict handling. Complete selected routine credential/readiness setup now rather than require a later dashboard visit. Noninteractive input retains protected boundaries, never ordinary secret arguments/chat. See [Wallet](wallet.md) and [project encryption](project-encryption.md).

## No check-command question

Remove the check-command question completely from the wizard, including script selection, custom-command prompts and a mandatory validation-deferral decision. Preserve an existing real `execution.check`. When no check is configured, create a successful informational placeholder such as `echo "Configure project checks in ptbk.json execution.check"` without asking the user. It explicitly means real automated validation is not configured, not that project tests passed, and does not block init/start or the first task.

An explicitly supplied `init --check COMMAND` can fill the missing setting without a question; preserve existing valid defaults and the usual temporary-override rules. Never replace a failing real validator with the placeholder to claim success. Expert may establish appropriate validation through ordinary work; see [checks](checks.md). Init itself does not run project checks or call a model.

## Optional synchronization and persistence

Add the **Automatic synchronization** step under [synchronization setup](synchronization-setup.md). Default/reused false asks nothing further. A new yes offers GitHub publication, private by default with explicit public choice, or a user-supplied other origin. Dedicated GitLab setup is future scope. Keep actual origin/upstream in Git, not duplicated JSON fields. Existing repositories/branches/remotes are not silently replaced.

Save the ordinary first task assigned to Expert and referring to `specs/_initial.md`; do not ask for a separate starter assignment. By default commit only authorized local setup before dispatch/publication, using an initial or scoped `ptbk: ` commit and applicable names. Preserve unrelated edits, hooks and signing. Failed local persistence is incomplete setup. Initial remote creation/push has an honest separate outcome: its failure leaves synchronization pending but does not prevent otherwise ready local work.

## Completion and automatic start

Successful local technical setup leaves selected initial tools and chosen credential imports usable within supported capabilities, required roles/storage present, original intent/assets and the ordinary bootstrap saved, and either preserved real validation or the explicitly labelled placeholder. Default setup is committed. Check the settings the service will actually use, not wizard-only state. Do not claim checks or publication succeeded merely because files or login windows were created.

Automatically perform the ordinary [background start](start.md) with the selected project and applicable explicit overrides. No extra Start confirmation is required. In ordinary interactive presentation, successful init then automatically hands off to the ordinary project dashboard unless `--no-dashboard` (or raw/noninteractive/no-UI presentation) suppresses that viewer. The daemon executes Expert and follow-ups through the normal queue; init does not execute them inline or wait for their checks/results.

Confirm the bounded service-start outcome. Interactive init then uses the short automatic/cancellable handoff to the same ordinary dashboard under [initialization UX](initialization-ui.md); `--no-dashboard`, raw/no-UI/noninteractive use returns directly. Cancelling/skipping the viewer handoff never stops the engine. `ptbk dashboard` and `ptbk stop` remain available. Distinguish local setup, service launch, task progress and pending synchronization. Launch failure preserves setup/queued work and gives the repair action; a later task failure is runtime work, not a reason to rerun init.

Explicit `init --no-commit` remains a labelled uncommitted setup/task workflow when no required migration or autosync conflicts with it; propagate that policy through the automatic start. Never claim a committed guarantee or silently switch policy. Later committed use follows [Git reconciliation](git-persistence.md).

Cancellation or unresolved essential local setup preserves progress without false success or hidden noninteractive prompts. A placeholder check is not unresolved essential setup, and a remote synchronization outage is not a local-launch prerequisite. Repeating unchanged init creates no empty commits, duplicate/reopened starter, repeated login or reset settings. Reuse a running service without overriding deliberate pause/draining intent; an explicit successful init on a stopped project includes the ordinary start. See [process modes](process-modes.md), [Git preflight](git-preflight.md) and [execution](execution.md).
