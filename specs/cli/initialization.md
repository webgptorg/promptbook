# Project initialization

[Main specification](../_main.md) · [Initialization experience](initialization-ui.md)

`ptbk init` (`ptbk initialize`) is a finite technical setup workflow for an empty folder or an existing project. It prepares project support, saves the initial specification and an ordinary bootstrap task, and starts the agenda in the background. Project-specific content is created by that task, not by a second execution mechanism inside the initializer. Presentation, progress, input controls and celebration belong to [initialization UX](initialization-ui.md), not this functional contract.

Initialization is reusable: start invokes the same readiness checks and missing setup steps. Reusing it from start must result in one start operation, not recursive init/start calls or duplicate workers. Equivalent setup decisions can be supplied in advance for noninteractive use.

## Initial input and destination

For a new initialization, the first question is what the user is working on, before destination, installation or other technical choices. Accept arbitrary project intent, not only software projects: free text, long pasted material, images and other attached files. A previously supplied input or an existing initialization's recorded intent is reused rather than asked for again. Reinitialization and upgrades preserve the existing project's purpose.

Then resolve the destination: current directory by default or a new subfolder, reusing an explicit destination. Confirm the resolved location before project writes. A nonempty destination is an existing project, not permission to regenerate it. A child inside Git follows [nested-project initialization](nested-projects.md). The optional [engine-update gate](updates.md) must not displace the initial intent question or lose its draft.

Save the accepted input in the initialized project's `specs/_initial.md`. Preserve the user's text verbatim, including its language, wording, whitespace, line breaks and long pasted blocks. Do not summarize, translate, improve or replace it with an AI-generated specification. Save attachments as project-local assets and reference them with working relative links at their corresponding positions; preserve their order and original contents. Composer placeholders are presentation only: saved text contains the full pasted material, not `[Pasted text ...]` labels. Do not leave references to clipboard state, temporary files or absolute paths on the originating machine.

These are the initialized project's specifications, not the engine's own specification directory. Prepare the input and assets as setup artifacts with the [first task](first-task.md). Never overwrite an existing initial specification or duplicate its attachments during resume/reinit. Blank input is allowed: preserve it as blank rather than invent a purpose; the first task then performs a bounded readiness review while preserving existing content.

## Incremental technical setup

Check Git, `ptbk.json`, agent/task/chat locations, project instructions, core agents, templates and ignore rules individually. Reuse a valid enclosing repository and its current branch, including one without a first commit; otherwise initialize Git. Resume only missing setup, preserving existing files and customization.

Prepare `agents/`, the configured task source (normally `tasks/`), `chats/`, `specs/`, root-level `traces/`, readable project instructions, required [core agents](../agents/core-agents.md), useful role/task templates and [configuration](configuration.md). Create only missing core agents. Default ordinary roles include Developer, Planner, Lawyer and Copywriter, with useful TEAM relationships. Keep `.ptbk/` ignored; trace ignore behavior instead follows the saved [trace settings](trace-configuration.md).

The required core roles include [Chatter](../agents/chatter.md), the default human-chat entry. Initialize a missing `agents/.core/chatter.book` with a small editable `AGENT Chatter` definition and TEAM access to all other roles initialized/selected for this setup, including core agents and specialists, without a self-reference. It may consult Expert for engine-specific questions. Build that initial team from the completed role set, not only the roles created before Chatter's file. Reinit/upgrade preserves an existing Chatter and its customized team; add missing definitions individually without resetting any other Book. Creating Chatter is technical setup, not an extra chat, model call or bootstrap execution.

Apply the destination-specific [local installation choice](installation.md). Configure only the selected harnesses, completing [setup](harnesses.md) and the separate [update choices](harness-updates.md) for each. Reuse healthy global installations and native authentication. Browser/profile selection is independent and presents **four explicit sources**; the **Promptbook-managed dedicated global profile** is the new default, reused across projects on the same machine without using the user's personal Chrome profile. See [browser](browser.md). Choosing no usable harness leaves setup incomplete, not ready to run. Resolve known access and execution-permission requirements during attended setup rather than defer routine approval prompts to the daemon; see [unattended operation](autonomous-operation.md).

Collect three trace settings and save them in `ptbk.json`: whether to commit traces, whether to Git-ignore trace videos, and whether to record browser video at all. Their dependencies and effective ignore behavior are defined in [trace configuration](trace-configuration.md). Reuse previously saved answers. Task evidence uses the literal source-filename directory convention in [traces](traces.md), independently of the task's declared logical name.

Resolve missing or unconfigured validation during init. Offer valid existing scripts, a custom command or explicit deferral; confirm the exact command saved in `ptbk.json.execution.check` or repair of its effective setting. Verify references and dependencies without running project checks or calling a model. A fresh skeleton includes meaningful working validation, not a generated failing placeholder or unconditional pass. Expert may later adapt validation to the project's content through ordinary checked work. `init --check COMMAND` supplies a missing check decision; valid saved defaults remain intact and an override follows [configuration precedence](configuration.md).

Save the [first runnable task](first-task.md), explicitly assigned to the engine-supplied Expert and referencing `specs/_initial.md`. Do not ask the user to compose a separate first task. By default commit authorized setup artifacts before dispatch, using an initial or scoped setup commit with a `PTBK: ` subject and applicable task names under [Git persistence](git-persistence.md). Preserve unrelated staging, edits, hooks and signing. A failed commit is incomplete setup, not success.

## Completion and automatic start

Successful default initialization leaves all selected harnesses usable, real saved validation and prerequisites available, required agents present, the initial specification, bootstrap task and chat storage saved, and authorized setup committed. Check readiness using settings the service will actually use, not wizard-only state. Created files or a launched login window alone are not completion. Do not claim project checks passed when init did not run them.

After technical setup succeeds, automatically perform the ordinary [background start](start.md) with the selected project and applicable explicit workflow overrides. There is no extra Start confirmation or manual Run action. A new project begins its Expert task through normal queue processing; the task can create follow-ups that continue through that same queue. Init does not execute the task inline or wait for it, its checks, or its follow-ups to finish.

Confirm the bounded service-start outcome and return the terminal. Do not attach a terminal dashboard or open a browser dashboard. The primary next-action hint is `ptbk dashboard`; `ptbk stop` remains available. Distinguish technical setup complete, service running, and task progress. If service launch fails, preserve completed setup and the queued task, report the failed launch and its repair action, and do not claim the agenda is running. A task failing after a confirmed launch is a runtime outcome, not a reason to rerun initialization.

Explicit `init --no-commit` preserves that policy through the automatic start. Label the uncommitted workflow and retain ownership, checks and recovery; do not claim the default committed guarantee or silently switch to committing. Returning to a later default invocation requires reconciliation under [Git persistence](git-persistence.md).

Cancellation, deferral or an unresolved prerequisite preserves completed progress but does not start work or report full success. Noninteractive init fails actionably for missing required decisions; it never waits on invisible prompts. Later credential expiry, outages or genuinely task-specific decisions remain possible; known setup problems are not deferred to runtime.

Reuse working native Codex ChatGPT authentication under the [account and billing rules](harnesses.md#codex-account-login-and-billing). Missing optional credit-control flags alone do not require another login, API key or `--allow-credits`; actual execution capabilities and provider quota remain distinct.

Repeating init with unchanged choices does not rewrite files, duplicate or reopen the first task, reset configuration, repeat login or create empty commits. Reuse an already running service without resetting its configuration or pause/draining intent; a successful explicit init on a stopped project includes the same start operation. Newer engines may add missing required artifacts without overwriting customization. Engine ownership and host discovery are handled by that ordinary start, not by attaching a dashboard. See [process modes](process-modes.md), [Git preflight](git-preflight.md) and [execution](execution.md).
