# Starting an ongoing agenda

[Main specification](../_main.md) · [Unattended operation](autonomous-operation.md)

`ptbk start` operates the selected project's agenda indefinitely without requiring per-task agent, harness, model or thinking-level selection. Successful [initialization](initialization.md) invokes the same background start automatically. Starting a ready project starts actual task processing, not just a daemon and HTTP server waiting for another Run action. A project has one executing task at a time, not one concurrent worker per agent.

Before execution, inspect initialization and readiness. For a missing or partial setup, explain what is missing and offer the same [initialization workflow](initialization.md) when interactive, with the already-selected project as its destination. Preserve completed steps and existing choices, then recheck readiness. Share one setup/start handoff rather than recursively starting another initializer or daemon. After successful default init, unchanged prerequisites require no more onboarding, harness login, check selection or task creation. Raw/noninteractive startup reports missing prerequisites and explicit repair actions instead of launching hidden prompts.

An unresolved project check enters the shared validation setup step even when every setup artifact already exists. Preserve valid checks and use supplied `--check` overrides for this invocation. A confirmed missing check becomes a saved project default; deferral leaves the service unstarted. Noninteractive startup identifies `ptbk.json.execution.check` and `ptbk init --check COMMAND` as concrete repair paths. Never treat a generated failing placeholder as working validation.

With no flags, start a background daemon, enable restart persistence and expose the lightweight dashboard on an automatically chosen loopback port, searching from 3000. Also establish [protected remote access](remote-access.md) through the default managed tunnel, with explicit `--no-tunnel` for local-only use and `--no-server` for neither. Serving a dashboard does not open or attach it. Tunnel connectivity is separate from task readiness: failures are visible and retried without indefinitely preventing safe local work.

An interactive launching terminal may complete missing setup before detaching. Discover project agents through the shared resolver and only project-enabled harnesses for routing, reuse their global setup and apply the configured [harness-update policy](harness-updates.md). Unselected installed harnesses are not implicit candidates; referenceable hidden/dependency agents do not automatically become goal-discovery candidates.

The default launch is a one-shot command: after a bounded startup outcome, render one polished result and release the terminal while the service continues. Do not automatically attach a live dashboard or open a browser page. `--raw` changes presentation, not daemon lifetime or tunnel enablement. Explicit `--foreground` keeps execution attached, using the [live terminal dashboard](terminal.md) when interactive or plain events otherwise. Browser/API clients show the same actual state and service version.

Render the [shared status snapshot](status-view.md) with confirmation, project/version, work phase, queue, prominent chats awaiting a user answer and a separate connection panel. A ready public HTTPS address and protected pairing QR are primary for opening on a phone; retain the clearly labeled local URL. Report connecting/degraded remote access separately from a running local service rather than show a misleading localhost mobile QR. Follow no-QR/raw/authentication rules and include useful next commands such as `ptbk dashboard`, `ptbk show` and `ptbk stop`. Do not wait for the first task to finish before returning. Init's finite final summary follows [initialization UX](initialization-ui.md), with dashboard as its primary next-action hint.

## Automatic work progression

Begin queue evaluation during startup and after each completed task, without waiting for a dashboard client. Execute eligible assigned tasks, including init's [Expert bootstrap task](first-task.md). For otherwise actionable tasks with missing routing, create and execute [Manager](../agents/manager.md) prerequisites automatically, then continue with their targets. Missing `TASK AGENT` is not a terminal blocker or a user assignment request; unavailable explicit requirements remain real blockers. Assignment and target work are serial, checked and committed by default, without recursive bootstrap or duplicate prerequisites.

[Authoring operations](authoring.md) commit new task sources before dispatch by default, so ordinary add followed by start does not require a manual commit. `--no-commit` is an explicit workflow exception under [Git persistence](git-persistence.md); keep it visible and never mistake its own pending writes for unrelated user changes or pretend it created commits. Unrelated or invalid initial state still requires safe reconciliation.

When no unfinished work remains, including future work, automatically enter due [goal discovery](goal-discovery.md). Execute useful generated tasks in the same session. Respect persisted cooldowns, future conditions, pauses and actual human/safety requirements. Show current work, automatic assignment/discovery, or a concrete reason for waiting and next action/opportunity when known. Do not manufacture progress or useless work to avoid legitimate idle time.

Follow the primary [unattended-operation contract](autonomous-operation.md): routine authorized actions and recoverable problems must not wait for repeated user confirmation or hidden harness input. Resolve known setup before detaching, recover automatically within budgets and request a person only for genuinely unresolved conditions, through the initiating agent's durable chat. Run [Fixer's](../agents/fixer.md) bounded health enquiries as ordinary scheduled maintenance alongside other real tasks, without elevating Fixer to a separate runtime subsystem. Safely checkpoint task-local blockers and continue independent eligible work without concurrent mutation. A project-wide blocker must identify why safe switching is impossible; an alive but needlessly stalled daemon does not meet this contract.

Once running, survive ordinary task, check, provider, tunnel, update and persistence failures. Recover automatically when safe, otherwise retain clear [errors and traces](errors.md) and stay controllable. Do not exit merely because the queue is empty or a task fails. The local agenda is intended to run for months without routine manual restarts; an ephemeral tunnel's uptime or hostname is not guaranteed for that duration.

Repeated start reports the existing process once without another supervisor/tunnel, repeat initialization, silent configuration replacement or dashboard attachment. Use `ptbk dashboard` to observe it continuously. See [controls](controls.md), [dashboard](dashboard.md), [persistence](persistence.md), [process modes](process-modes.md) and [run](run.md).
