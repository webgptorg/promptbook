# Unreleased

## Reborn `ptbk` implementation

-   The repository publishes exactly one npm package, `ptbk`, installing the `ptbk` CLI (global or project-local).
-   Fresh implementation from [the specification](../specs/_main.md):
    -   Book language parser (agents and tasks), four-tier agent resolution, inheritance, IMPORT/DELETE, learning policy.
    -   Task Books and Markdown tasks, eligibility, priorities, dependencies, earliest start, recurrence.
    -   Harness plugins: OpenAI Codex, Claude Code, GitHub Copilot, Cline, OpenCode, Gemini CLI, Qwen Code (featured/More catalog).
    -   Execution lifecycle with checks, repair budgets, single `PTBK: <task title>` result commits, Manager assignment, Teacher learning, goal discovery, user requests via the ptbk MCP bridge (TEAM consultations), recovery.
    -   `init` wizard and unattended flags, `start`/`stop`/`restart` daemon with supervisor and OS startup persistence, foreground mode, finite `run`.
    -   Live terminal dashboard, shared status view, lightweight browser SPA and authenticated HTTP API (pairing, sessions, API tokens, CSRF), Cloudflare tunnel management.
    -   Shared project browser (Chrome via CDP) with agent tools.
    -   Commands: `add`, `answer`, `list`, `plan`, `fix`, `verify`, `migrate`, `recover`, `lint`, `access`, `ping`, finders and boilerplates.
-   Release flow: `npm version …` runs basic checks in `preversion` and pushes the version commit and tag in `postversion`; GitHub Actions (**Check ptbk**, **Publish ptbk**) validate and publish.

## Autonomous initialization and task audit trails

-   `ptbk init` is intent-first: the first question asks what you are working on, using a rich composer (multiline text, compact `[Pasted text #n, N lines]` tokens, `[Image #n]`/`[File: …]` attachments via drag-and-drop paths, Ctrl+O and clipboard images with Ctrl+V; tokens can be inspected, expanded with Ctrl+T or removed). The input is preserved verbatim in `specs/_initial.md` with project-local attachments in `specs/_initial/`; noninteractive equivalents are `--intent`, `--intent-file` and repeatable `--attach`.
-   Init saves one ordinary Expert task (`TASK AGENT @Expert`) linking the initial specification (a readiness review for blank intent) instead of a generic starter, commits setup with its `Task-ID`, then automatically performs the ordinary background start (explicit overrides such as `--no-commit`, `--no-tunnel`, `--port` and `--no-persist` carry over; `--no-start` only prepares). It never executes the task inline and returns immediately; `ptbk dashboard` is the primary next step. Repeated init reuses a running service; an explicit init also resumes an intentionally stopped one.
-   Wizard experience: truthful `Step X of Y` that updates when the path changes, Expert as the visible procedural guide, Esc goes back (drafts survive), Ctrl+C cancels, a dedicated **Traces** screen, and a brief celebration after confirmed success (static with `PTBK_REDUCED_MOTION`, none in raw output). An engine self-update keeps the accepted intent and attachments as a draft for the rerun.
-   Stable task IDs: every new task gets one (add, plan, verify, finders, Manager, Teacher, discovery, follow-ups written by agents); legacy tasks receive theirs in a scoped `PTBK: Assign task ID - …` commit before execution, never during list/dry-run. Markdown sections carry `<!-- ptbk-task-id: … -->`; duplicates (case-insensitive) and path-unsafe IDs are errors; copied IDs in new follow-ups are replaced; migration preserves IDs.
-   Commits carry `Task-ID` trailers (plus `Created-Task-ID`/`Related-Task-ID` for follow-ups and assignment targets) on creation, assignment, preparation, result, failure and setup commits.
-   Per-task audit trails in root-level `traces/<task-id>/`: consolidated readable harness output for every attempt, occurrence, TEAM consultation and check (`harness.log`), task events (`events.jsonl`), post-commit events (`local/`), and browser recordings (`video/`, status in `video.json`) with page transitions, secret-entry/sign-in gaps and MP4 (via ffmpeg) or dependency-free Motion-JPEG MOV. Trace settings `traces.commit`, `traces.ignoreVideos`, `traces.recordVideo` drive a managed `.gitignore` block; committed traces share the task's result commit. Trace snapshots are never agent definitions. `ptbk list <task>` shows a task's trace, video and commits.
-   Unattended operation: a task waiting for a person (question or failure decision) is checkpointed and independent work continues when it holds no uncommitted changes (otherwise the wait is shown as a project-wide blocker); an answer resumes it automatically. Duplicate requests are merged and record what was already attempted. Agents are told not to ask for routine confirmation. Harness subprocesses that stay silent (`execution.stallTimeout`, default 45m) or silently wait on a terminal prompt are stopped and retried. Codex runs pre-approve ptbk's own MCP tools (`default_tools_approval_mode="approve"`), so `ask_user` and browser tools are no longer rejected as "approval unavailable".

## Agent references

-   Specification: agent references are `@Name` for single-word names and `{Multi Word Name}` for multiword names (`@Adam` and `{Adam}` are the same), used everywhere including `FROM @Void`, `FROM @Expert` and `FROM @Developer`; the resolution order (built-ins `@Void`/`@Null`/`@Expert`/`@User`, then `agents/`, the rest of the project, then Git-ignored content such as `node_modules`) is illustrated with example Books. Bare names in FROM stay accepted for compatibility.
-   Supplied core Books use the `@` form: Adam is `FROM @Void` and now ends with `CLOSED`; Teacher is `FROM @Expert`. The default Developer consults `@Expert` when writing `book` language. Existing projects' core Books are not rewritten.

## Names, chats and Fixer

-   Agents, tasks and chats are one kind of Book: the first nonempty line is the name and identity, `ENTITY AGENT|TASK|CHAT` declares the kind (the `agents/`, `tasks/` and `chats/` folders supply it otherwise; legacy `TASK <title>` headers still read as a task named `<title>`). New `LINK`, `CHAT MEMBER`, `CHAT STATUS` and `CHAT MESSAGE` commitments.
-   One deterministic resolver for every reference (`@Name`, `{Multi Word}`): built-ins, then `agents/`, `tasks/`, `chats/` (shallow first), the rest of the project, then Git-ignored content. Same-name Books are shadowed with a diagnostic instead of merged, renamed or reported as ambiguous; a reference to the wrong kind is an error. `ptbk lint` also checks LINK and chat members.
-   Task IDs are gone (this supersedes the stable task IDs above): tasks are identified by their normalized name, new work gets readable distinct names, legacy `TASK ID`/`ptbk-task-id` values are kept only as historical metadata (`ptbk list "#old-id"` still finds them). Commits carry `Task-Name`, `Created-Task-Name`, `Related-Task-Name` and `Chat-Name` trailers; evidence lives in `traces/<name-key>/`; `ptbk migrate` writes canonical `ENTITY TASK` Books and refuses name collisions.
-   Chats replace the separate request store: questions, sign-in requests and failure decisions are chats started by the responsible agent, linked to their task; the task checkpoints and resumes only on a valid answer (recovery decisions accept only their offered answers; other messages are clarifying questions the agent answers). Every human-facing message is its own commit; reading, opening and read markers never commit; stale clients are rejected by message-count revision checks. Pending requests of older engines are migrated into waiting chats once.
-   New `ptbk chat` (choose the agent first: project agents, or More for hidden/core agents and Expert; `--agent`, `--open <name>`, `--list`; Ctrl+C closes only the client) and `ptbk ask`; `ptbk answer` now lists and answers waiting chats. Chats work with or without a running service; agents reply read-only, create ordinary linked tasks through `create_task`, and a correction schedules an ordinary Teacher task (`TASK ORIGIN learning from chat {…}`). The service also replies to user messages written while it was stopped.
-   Dashboards: terminal `A` opens the conversation of the agent waiting for you, `C` starts a new chat, `L` lists all chats; status shows chat attention (waiting and unread). The browser dashboard and HTTP API gained chat list/new/open/reply (`/api/chats`, `/api/chats/<name>/messages`, `/api/chat-agents`).
-   Fixer is the fourth core agent (`agents/.core/fixer.book`, OPEN, consults @Expert); existing projects receive it without other Books being touched. When the project has health findings (Book syntax, name collisions, unreadable tasks, chat syntax, configuration), the agenda schedules one ordinary Fixer task — after the findings change (at most hourly) or daily while unresolved — and never without findings.
-   Browser profiles: `browser.profile` is `global` (new default: a dedicated Promptbook profile in the OS application-data folder, reused by your projects one at a time and released after each task), `isolated` (`.ptbk/`), `user` (your Chrome profile) or a custom path; init offers all four. Saved choices are kept.

## Typed Book declarations and generated names

-   One Book grammar for agents, tasks and chats: every Book starts with exactly one `AGENT <name>`, `TASK <name>` or `CHAT <name>` declaration whose content is the name; the kind comes from the declaration, never from the folder. A commitment keyword is the complete line-initial sequence of uppercase words (at least three letters), so `TASK AGENT` and `CHAT MESSAGE` are not declarations, `A`/`I`/`AI` starting prose never begin commitments, and unknown keywords (`TASK SOMETHING`, `RULE API …`) are preserved and diagnosed instead of being shortened to a known prefix. A name is a single line; text directly under it is invalid (descriptions go under GOAL, PERSONA or NOTE). `GOAL` now also describes a task's bounded work. A leading backslash or a fenced block keeps content literal; generated content is escaped losslessly.
-   This replaces the previous `<name>` + `ENTITY` form: plain name lines, `ENTITY` and introductions are former syntax — diagnosed (lint, Fixer, a start-up warning, blocked tasks in `ptbk list`) but never used or rewritten silently. `ptbk migrate` now also converts them explicitly (one maintenance commit), keeping names, content and history: descriptive text moves under GOAL (tasks), PERSONA (agents) or NOTE (chats), redundant ENTITY lines are removed, an ambiguous kind or a name starting with an all-uppercase word is reported instead of guessed. Markdown migration writes `TASK <existing name>` with the payload under GOAL.
-   References: `{{Multi Word Name}}` is the canonical brace form (single braces still read); generated references, links, origins and messages use it.
-   Generated names: every newly created task or chat — `ptbk add`, `plan`, `verify`, finders, `fix`, init's first task, Manager/Teacher/Fixer/discovery/repair tasks, tasks created from chats, `ptbk chat`/`ask`, dashboard/API chats, agent questions and consultations, boilerplates — is named `<title> — <YYYY-MM-DD HH:MM:SS>` in the project's time zone, made distinct from every Book after normalization (with ` (2)` etc. when needed) and rechecked when published, including by the running service for `ptbk add`. A name whose first word is all uppercase is recased (`API cleanup` → `Api cleanup`). Reopening, replying, retrying, recovering, recurring or rerunning init never renames anything; undated names stay valid. Retried API chat creation with the same `requestKey` returns the original chat.
-   Agents writing follow-up tasks are told the canonical format and the current creation time; a new task Book that is invalid or reuses an existing name is sent back for repair before the result is accepted.
-   Core agents and default roles are written as `AGENT …` Books; core agents are created only when no Book uses their name. `DELETE RULE …` is recognized as one complete keyword. Init's first task is recognized by its origin on reinitialization.
