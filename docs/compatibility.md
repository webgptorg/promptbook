# Coder compatibility and verification

This record maps the implementation to [the coder specification](https://github.com/webgptorg/promptbook/blob/main/specs/coder.md). The scenario IDs below identify related requirements; they do not certify every combination in an acceptance scenario. Fixture coverage, provider capability checks and live-provider verification are different forms of evidence.

## Deliberate changes and limits

- Runtime support is Node 22.13+ within the Node 22 line, or Node 24+, with npm 10+ and Git. macOS and Linux are target platforms; native Windows is not claimed. Windows use is documented through WSL.
- Operational files moved to `.promptbook`; task Books are preferred for new work. Existing Markdown runs without migration. Older binaries cannot execute the new Books, and reverting Git does not restore the unversioned recurrence ledger or external effects.
- Developer remains the default execution/planning role. List without `--agent` does not implicitly filter to Developer. Agent, harness and model are separate selections.
- Authoring commits are opt-in. Execution commits only proven phase scope; automatic `--no-commit` requires `--git-changes ignore`. Pull and push remain explicit.
- Codex account execution fails before inference when the installed CLI cannot enforce the default prohibition on account credits. `--allow-credits` is explicit authorization; API billing needs its separate opt-in. Current provider capability checks can reject a configured workflow before a paid call.
- Agent executable capabilities outside the supported Book subset, model sampling parameters and binary/PDF knowledge are rejected. Planning currently supports only a Codex CLI advertising the required controls; TEAM support requires actual bridge discovery and safe advisor permissions. Qwen/Cline require an agent without TEAM, including when init's default Books contain TEAM. OpenCode TEAM requires explicit `--model provider/model`.
- Parallel task workers, unified Agents Server/SQLite, natural-language/event triggers, cross-clone claims, origami avatars, automatic quota-threshold switching and a marketplace are deferred. Test-server database migration has no bundled project adapter and is rejected when unconfigured. Task dependency syntax is not implemented and does not silently become runnable.

## Verification record

On 10 October 2026, before the release lifecycle changes, `npm run check` passed on macOS with the minimum supported Node `v22.13.0` and npm `11.13.0`: TypeScript validation, all 125 deterministic fixtures, and the actual tarball installed both locally and globally in an external project. The same full check passed on Node `v24.17.0` through the earlier local publication attempt's `prepublishOnly` lifecycle. The package smoke also executed a task through a harness double, ran checks, and verified phase commits.

After the lifecycle changes, all 15 focused `test/version.test.mjs` fixtures passed using real npm commands and local bare Git remotes. They cover exact atomic pushes, upstream selection, failure preservation, dirty/detached preflight rejection, retry and the explicit Git-tagging opt-out. The updated full `npm run check` passed on macOS with Node `v24.17.0` and npm `11.13.0`: type checking, all 141 fixtures, and the packed `ptbk@0.115.0-1` installed locally and globally with external-project task execution, checks and phase commits.

After adding registry propagation polling, the full check passed on the same macOS Node/npm versions with all 150 fixtures and the packed `ptbk@0.115.0-2` installation smoke. The nine new deterministic fixtures cover temporary missing-version/network responses, stale dist-tags, timeout bounds, authentication failures and invalid artifact metadata without real waits.

The workflow defines macOS/Linux checks on Node 22 and 24. The `v0.115.0-2` publish job passed all 141 fixtures and package smoke on Linux with Node `v24.21.0` and npm `11.19.0`. WSL/native Windows, paid real-provider inference, remote advisor inference and a manual full terminal session have not been verified here.

Control-only native startup probes, without user prompts or paid model turns, verified tool discovery with Codex `0.162.0`, Claude Code `2.1.289` and Copilot `1.0.95` (matching published SDK `1.0.19`). Cline `3.0.70` also discovered an idle MCP server under a real TTY, but its tool permissions do not establish safe advisor capability. Gemini/Qwen ACP and OpenCode discovery controls were reviewed against primary sources and tested with executable doubles; they were not live provider-inference tests.

An earlier local `npm run release:publish` attempt prepared `ptbk@0.115.0-0` but failed with `ENEEDAUTH` and uploaded nothing. Publication now runs only in GitHub Actions, triggered by the version commit/tag that local `npm version` atomically pushes. The [first tagged publish job](https://github.com/webgptorg/promptbook/actions/runs/38018816282/job/114115037379) successfully uploaded `ptbk@0.115.0-2` with provenance, but the immediate registry query returned E404 while npm processed the artifact. A later `npm run release:verify` passed: the public version, its historical `next` tag, SHA-512 metadata and exact-version local/global installs all matched. The [following publish job](https://github.com/webgptorg/promptbook/actions/runs/38021247222) successfully published `ptbk@0.115.0-3` to `next` with bounded propagation verification. Those releases left the default `latest` tag pointing to the legacy `0.114.0-50` package. The release policy now restores `latest` for normal version releases and verifies unversioned local/global installs to detect this default-install mismatch. Verification still waits for bounded registry propagation instead of failing on the first temporary response. A failed postversion push can be retried with `npm run postversion`; after an accepted upload, use `npm run release:verify` without attempting to overwrite the npm version.

For usage and release setup, see [the coder guide](coder.md). Fixture evidence is maintained in the repository's `test/` directory; the npm package ships the runtime and user documentation rather than the test suite.
