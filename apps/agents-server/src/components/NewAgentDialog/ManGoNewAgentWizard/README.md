# manGo creation sessions

`useNewAgentDialog` owns each explicit `MANGO_WIZARD` opening. It creates a random identity before mounting the wizard, ends the previous session synchronously, and mounts the provider with that identity. Start-over uses the same state factory while preserving the host's folder, visibility and mode. Account/server scope changes abandon the previous draft.

The provider exposes a session-owned in-memory store. Back/Next, rail navigation and provider remounts retain assignment inputs, edited Books, knowledge associations, test conversations/evaluation, pending operations, errors and saved identity. Local editor/file-input resources are mounted under the creation identity. No implicit draft recovery is supported after closing, cancelling, completing-and-leaving, or reloading the page. A later **New agent** action always starts empty. A deliberate classic-editor handoff carries only the current composed Book and the host's folder/visibility settings.

The old `onboarding:v2` snapshot is never read. Only that obsolete wizard entry is retired when opening manGo; unrelated drafts, authentication, storage and caches are untouched. Creation does not require browser storage, so malformed entries, blocked storage and exhausted quotas cannot restore another agent or prevent creation. There is no session snapshot to copy into another tab or authenticated-user/server scope.

Session operation tokens combine lifetime ownership with a request revision. Superseded generation/test requests and removed uploads are aborted where supported, and all results, failures and settlement callbacks also check ownership. Concurrent uploads have separate item tokens. Editing the assignment or Book supersedes a pending generation without erasing manual edits; explicit generation reads the latest assignment. Ordinary navigation retains the Book. Editing test inputs or Book/knowledge supersedes pending test/review work.

Saving uses the existing create-agent action, permissions, folder and visibility semantics. The session owns duplicate-submission protection across step/provider remounts and effect replay; failures retain the draft for explicit retry. Success is recorded before host notification, and completion retains its canonical identity for the correct chat action. Even if a server save finishes after cancellation, that outcome belongs to its original operation; it neither closes the replacement dialog nor deletes/retries the created agent. Reset removes draft associations and transient resources without deleting uploaded objects.

## Reproduction and verification

Source inspection confirmed that the former provider hydrated every mount from `onboarding:v2`; Book generation skipped any nonempty restored Book, and completion reused any restored saved identifier. Client generation sends only the supplied name/brief to `/api/onboarding/book`. The server helper constructs a new `LiteAgent` per invocation; no shared backend agent or cache change is needed.

The two legacy-snapshot cases in `ManGoSession.integration.test.tsx` were executed against the host/provider/steps from `cc82cd1c97d8bc1cdb251d401a0ab62a29c296f1`, substituted by a temporary Jest transformer without changing the workspace sources. Both failed: after entering B's name/brief, its editor still contained A's Book and `KNOWLEDGE` marker, including for a completed snapshot. This was a deterministic React/jsdom reproduction, not a browser run or paid model call. Both cases pass with the session implementation.

`ManGoSession.integration.test.tsx` exercises the actual controller, provider, navigation and steps with deterministic generation/upload/persistence boundaries. `state/createOnboardingSession.test.ts` verifies independent collections/revisions, stale cleanup and the ownership of a late successful server save. `tests/e2e/mango-session-isolation.spec.ts` exercises the real browser, editor and host entry points with fixture AI/upload routes and the existing E2E mock database. It reads saved Books independently through the Book API and compares A after B/C creation. No production agents, real user uploads or paid model calls are involved.
