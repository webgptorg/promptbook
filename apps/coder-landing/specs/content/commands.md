## Option reference (context for copywriting)

These `ptbk coder` options may be referenced in page prose and must be described accurately:

-   `--harness <name>` — selects the coding agent; one of the harnesses in [`harness-catalog.md`](./harness-catalog.md). Required for non-dry runs.
-   `--model <model>` — model passed to the harness; **required** for `openai-codex` and `gemini`.
-   Prompt routing — add one or more backtick-delimited model, model-family, or harness names to a ready `[ ]` status line, for example `` [ ] use model `gpt-5.5`  ``; the prompt runs only when the selected harness or model matches after normalization, while `!` markers can appear before or after the token.
-   Prompt statuses — `[-]` not ready, `[ ]` ready, `[^]` being implemented right now, `[x]` implemented, verified and committed, `[!]` failed. `run` and `server` rewrite `[^]` before every step of a round, so it names the harness, the model, the finished steps and the running one (for example `` [^] by OpenAI Codex `gpt-5.6-luna` thinking `max` (ChatGPT account) - Implementation ~$0.2036 10 minutes; Testing in progress ``). Only the final `[x]` is committed, and `[^]` is never reverted, so a killed or crashed coder leaves it behind as the signal that the task was left in the middle; such a prompt is not picked up again automatically.
-   `--thinking-level <level>` — reasoning effort for supported harnesses: `low`, `medium`, `high`, `xhigh`, `max`.
-   `--agent <path.book>` — a `.book` file whose compiled system message is prepended to each coding prompt.
-   `--context <text-or-file>` — extra instructions inline or from a project file (e.g. `AGENTS.md`).
-   `--test <command...>` — verification command run after each prompt; failures are fed back and retried.
-   `--test-before <no|yes-and-fail|yes-and-fix>` — run the test command before coding; stop on pre-existing failures or create one repair prompt, and use `npm test` when no `--test` command is provided.
-   `--dry-run` — print unwritten prompts without executing.
-   `ptbk coder ping` — send one tiny dummy prompt to the harness and model selected with `--harness`, `--model` and `--thinking-level` and report the answer, the response time and the reported usage. It runs no coding task, writes nothing and commits nothing, so the project is left exactly as it was; `--allow-credits` and `--no-ui` behave as for `run`, where `--no-ui` streams the raw harness output instead of the compact result.
-   `--period <duration>` — `ping` only; instead of pinging once, keep pinging once per period until the process is stopped with `CTRL+C`. The duration uses the same format as the `--wait-*` options (`5h`, `30m`, `1h30m`) and must be positive. The period is measured from the start of one ping to the start of the next one, so `--period 5h` really pings every 5 hours regardless of how long a ping takes, and a failed ping is reported without ending the loop. Its main use is keeping the 5-hour quota window of Claude Code permanently open for the price of a few tokens per ping.
-   `--min-priority <n>`, `--max-priority <n>` — for `run`, process only prompts within the inclusive priority range; `--priority <n>` remains an alias for `--min-priority`; for `add`, `--priority <n>` sets the priority of the new prompt (rendered as trailing `!` markers).
-   `--limit <n>` — stop after N prompt runs (`run` only).
-   `--count <n>` / `--count <n>*<m>` — `generate-boilerplates` only; number of generated prompt files, optionally with the number of prompts written into each of them. `--count N` is the same as `--count N*1`, the default is `5*1`, and more than one prompt per file is an advanced option: each of the `M` prompts is a separate task, separated by a `---` line, and shares the file's fresh emoji tag.
-   `--no-auto` — wait for user confirmation before each prompt.
-   `--no-commit`, `--git-changes <mode>`, `--auto-push`, `--auto-pull` — git behavior switches of `run` and `server`, which commit every successful round by default.
-   `--git-changes <fail|ignore|continue>` — what happens when the working tree has uncommitted changes before a prompt starts. `fail` (the default) refuses to start and asks for a commit, a stash or one of the other two modes. `ignore` starts anyway and leaves the changes where they are. `continue` resumes the prompt an interrupted coder left behind in the `[^]` status, keeping its half-finished changes in place; it expects **exactly one** `[^]` prompt and fails when it finds none or more than one. Only that first round runs on the dirty tree, every later round expects a clean one again, and `continue` cannot be combined with `--isolate`, whose fresh worktree would leave the uncommitted changes behind.
-   Prompt status attribution — a prompt one harness started and another one continued records them in chronological order, as `` by OpenAI Codex `gpt-5.6-luna`, interrupted, continued by Claude Code `claude-opus-5` ``, in its `[^]`, `[x]` and `[!]` status line alike. Every later continuation appends another `interrupted, continued by …` report instead of dropping an earlier harness.
-   `--order <from-earliest|from-latest|random>` — `verify` only; order in which the prompt files are walked through. `from-earliest` (the default) starts with the oldest prompt file, `from-latest` starts with the newest one, and `random` shuffles the queue for every pass.
-   `--commit`, `--auto-push`, `--auto-pull` — git synchronization of `init`, `add`, `generate-boilerplates` and `verify`, which never touch git unless these flags are used. `--auto-pull` pulls before the command changes anything, `--commit` commits the resulting changes with the coding-agent git identity, and `--auto-push` (which requires `--commit`) pushes the created commit. For `verify` the synchronization is applied around each single verification instead of once per run.
-   Every commit `ptbk coder` creates contains **only the files of the operation which created it** — the added prompt file for `add`, the archived or repaired prompt file for `verify`, the prompt file together with the files the coding agent has changed for `run` and `server`. Changes which were already in the working tree before the command started are left there, so an unrelated work in progress is never swept into a coder commit.
-   `--isolate` — `run` only; implement each prompt in its own temporary git worktree (`.promptbook/coder-isolation-worktrees/<task-name>` on branch `ptbk-coder-isolation/<task-name>`) with its own copy of `.env`. A verified task is merged back into the current branch as one commit and the worktree is deleted; a task that cannot be merged is marked `[!]`, the failure is committed, and its worktree is kept for a manual merge while the coder continues. Because the worktree nests the whole repository one level deeper, git long path support is enabled for the isolated run so that Windows `MAX_PATH` does not break the checkout. Cannot be combined with `--no-commit`.
-   `--wait-after-prompt`, `--wait-between-prompts`, `--wait-after-error <duration>` — wall-clock pacing; durations like `1h`, `30m`, `5s`; pause and computer sleep count against the wait; `S` skips whatever the coder waits for while `S Skip current waiting` is offered, which besides these three waits covers the harness session-limit wait and the `server` keep-alive poll; errors retry up to 3 times (default wait `10m`).
-   `--no-ui`, `--preserve-logs` — plain streaming output / keep temp artifacts.
-   `--port <port>` — `server` only; kanban UI port, default `4441`.

Environment variables that may be mentioned: `CODING_AGENT_GIT_NAME`, `CODING_AGENT_GIT_EMAIL`, `CODING_AGENT_GIT_SIGNING_KEY` (agent git identity, created by `ptbk coder init` in `.env`), and `PTBK_HARNESS` / `PTBK_MODEL` / `PTBK_THINKING_LEVEL` as defaults for the corresponding options.
